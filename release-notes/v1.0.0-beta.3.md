Third **beta** on the `1.0.0` line. Two new Portable skills, `qa-plan` and `manual-qa`, cover manual QA of a pull request: one writes only the checks a passing CI run would not prove, the other runs that plan and reports. No reusable-workflow inputs, secrets or permissions changed, and no existing skill changed.

### Consumer action

- **None required.** Upgrade the `uses:` pins and the Kit-owned paths together, as always. From a clean branch in your repository:

  ```bash
  npx @mnaimfaizy/agent-kit@1.0.0-beta.3 upgrade --tag v1.0.0-beta.3
  ```

  It replaces the Kit-owned paths (which now include `.claude/skills/qa-plan/` and `.claude/skills/manual-qa/`), rewrites the Agent-kit pins, prints the `examples/` diff for you to apply to your Callers by hand, and runs the `doctor --ci` checks. It commits nothing; review `git diff` and commit.
- **To use the QA skills without adopting the kit,** install them from this tag into your own skills directory:

  ```bash
  npx skills add mnaimfaizy/agent-kit#v1.0.0-beta.3 --skill qa-plan -g
  npx skills add mnaimfaizy/agent-kit#v1.0.0-beta.3 --skill manual-qa -g
  ```

  Both are User-scope and need Node 22 or later. Don't use `npx skills` in a repository that adopts the kit; `upgrade` already copies them there. See [`docs/install-skills.md`](https://github.com/mnaimfaizy/agent-kit/blob/v1.0.0-beta.3/docs/install-skills.md).

### Added

- **[QA guide](https://github.com/mnaimfaizy/agent-kit/blob/v1.0.0-beta.3/docs/qa.md)** (`docs/qa.md`): the developer → QA team handoff end to end, the readiness check, targets and the host rule, the QA Account contract with a minimal seeder outline, Hazard packs, and posting. Start here. Templates to copy: [`examples/qa.config.yml`](https://github.com/mnaimfaizy/agent-kit/blob/v1.0.0-beta.3/examples/qa.config.yml), with every key of both skills, and a sample Hazard pack, [`examples/qa-hazards/sign-in.md`](https://github.com/mnaimfaizy/agent-kit/blob/v1.0.0-beta.3/examples/qa-hazards/sign-in.md).
- **`qa-plan`** (`/qa-plan`, on an open pull request) writes a **QA Plan** of the **Residue** only.
  - It runs each configured suite at the head and at the merge-base with `two-point.mjs` and compares their JUnit XML test by test. A regression stops it. Each coverage claim is tagged `[observed]` or, when a suite has no JUnit or the merge-base won't build, `[reconstructed]`.
  - An empty Residue is a valid result: it recommends merging without a plan.
  - The draft stays in a gitignored working directory until you confirm. Then it is kept as a working copy, or posted to one tracker issue per subject or one pull request comment, and edited on each revision. No credential ever goes in a plan.
  - **Hazard packs**, Markdown files you own with `when:` globs, add _Rule out first_ checks to matching scenarios and capture rules to the plan's Run brief.
- **`manual-qa`** (`/manual-qa`, on a QA Plan) runs it as written and writes a **QA Report** with an evidence folder.
  - It never composes, refuses a plan that carries a credential, and checks the build against the plan's head (or marks the report **build not verified against plan**).
  - Targets: a local **QA Stack** from your `up`, `migrate`, `seed` and `down` commands, or a hosted test environment someone else deployed (`target: url`), where it starts nothing.
  - **The host rule.** It signs in only to a local development host, or to a host with a test-environment label in its subdomain (`staging`, `qa`, `preview`, …) once the QA person names or confirms it in chat. Anything that looks like production stops the run. Role values come from your seeder or from the QA person in chat, never from an env file.
  - Each scenario is PASS, FAIL or _left for a person_; it never passes a _left for a person_ scenario itself.
  - Posting happens only with `gh` and after you say yes: one `<!-- qa-report -->` pull request comment, edited on each re-run, or ticks on the plan's tracker issue. **QA Artifacts** stay local unless `run.evidence.upload` is `gh-release:<tag>`, and then only the files you pick.
- Settings for both skills live in one `qa.config.yml` (or `.yaml` / `.json`) at your repository root, with a `plan:` and a `run:` section. Each skill asks for a missing setting and writes your answer to the file only if you agree.
