# Agent-kit threat model

Threat pack for the dogfood security audit of this repository. Scope is the kit itself: reusable workflows, their helper scripts, the read-confinement hook, the Portable skills, and the `agent-kit` CLI, whose `deep-scan` launcher runs a Deep scan in a sandbox on a maintainer's machine or on a GitHub-hosted runner. Consumer-side threats (their product code, their secrets) are out of scope.

> Draft. Review and adjust before enabling the dogfood audit.

## Trust boundaries

1. **Issue / PR text → agent.** Untrusted. Fenced in the brief; only the Verified plan is actionable for implement.
2. **PR head → review/audit runtime.** Untrusted. Instructions, skills, and the read-confinement hook are restored from the PR base before the agent runs.
3. **Agent workspace → credentialed steps.** The agent can write the workspace; later credentialed steps must only run scripts staged from a trusted commit and digest-checked.
4. **Agent → runner filesystem.** Read/Glob/Grep are confined to the workspace by the PreToolUse hook; `.git/` reads are denied.
5. **Caller → reusable workflow.** Caller-owned inputs (`scan_command`, `verify_commands`, `format_commands`, `setup_commands`, `extra_allowed_tools`) run with job privileges; they are trusted but must not be derivable from issue/PR text.
6. **Maintainer → tag.** Only the default branch is tagged; tags are never moved.
7. **Default branch → Deep scan.** The Scan recipe, `DEEP.md` and the Threat pack say what runs and what may be probed. They are trusted like Caller inputs (boundary 5), so they are read from the default branch's tip only: never the working tree, the checked-out branch, a pull request head, or issue/PR text. A Verification run (`--verify`, local only) still reads them there, so a fix branch cannot change how its own fix is checked. A recipe never holds a limit, a compose file or sibling container, the Docker socket or a real credential.
8. **Launcher → sandbox, locally and in CI.** Everything inside the sandbox is untrusted: the target, and the agent once it has read the target's output. The launcher runs it only on a runtime whose target shares no kernel with the host (Docker Sandboxes; Kata, Firecracker or gVisor on Linux, on Docker Engine 28.0 or later), chosen by checks made from the host, never inside, with no override. A Mac uses Docker Sandboxes: Docker Desktop for macOS is refused, as it has no way to keep a container from the host's services. In: an export of the default branch's tip, or of a Verification run's `--ref` (`git archive`, never a mount), the recipe's `grounding`, the launcher's brief, a Verification run's finding file (with the brief, after the network cut) and the run's caller key in place of a real key; no host folder, host env, Docker socket or extra privilege. On Docker Engine copy-in runs the sandbox's own `tar` as root, so for what goes in after setup ran (the brief, a Verification run's finding file) a hostile setup step could replace `tar` and alter it on the way in; that is accepted, as the target already controls the sandbox the agent runs in, and only the checked report comes out. Out: one report file, a single regular file of at most 10 MiB. Teardown destroys the rest on every exit path.
9. **Sandbox → network, setup phase.** `setup`, `start`, `ready` and `seed` run with no agent and no model credential, on a network whose only way out is the launcher's egress proxy, which forwards only to the recipe's `registries` (on Docker Sandboxes, a per-sandbox allow rule under a deny-all global policy). On Docker Engine the sandbox's one network is attached at `docker run` and never connected or disconnected after (a running gVisor sandbox would not see it); it is `--internal` and in the `isolated` gateway mode, so the host has no address on it, and the sandbox reaches the proxy only through a launcher-owned relay that forwards one TCP port. Before the target starts the launcher checks from the host the network's mode, that the sandbox is on it alone, and, with a probe container under the sandbox's own runtime, that the relay's port is reachable and the host is not, on the proxy's port or another ([What goes into and out of the sandbox](../docs/security-audit.md#what-goes-into-and-out-of-the-sandbox)). The cut stops the egress proxy and removes the setup relay, and a probe proves neither it nor the host is reachable before the agent step.
10. **Sandbox → model proxy → model API.** The agent's only route out is the key-injecting model proxy on the host, reached on Docker Engine through a second relay on the sandbox's same network, checked before the agent step by a probe under the sandbox's runtime that reaches that relay and nothing else; on Docker Sandboxes, through a per-sandbox rule for the proxy's port alone ([What goes into and out of the sandbox](../docs/security-audit.md#what-goes-into-and-out-of-the-sandbox)). The relay only forwards bytes: the real key never enters it. The proxy forwards only `POST` to the Messages API's own two paths, to `api.anthropic.com`, and only from the caller holding the run's caller key; it reads each body before sending it and refuses a server-side tool, `mcp_servers`, a `container` and content naming a URL or file for the API to fetch, so the model API acts on nothing outside the request. It strips the `x-api-key` and `Authorization` headers the sandbox sends, inserts the real key, and holds the cap with at most four requests in flight, each reserving its declared output and an estimate of its input. The real key crosses only outward, to the model API, and stays in the proxy; model traffic crosses only here, and the route closes when the agent step ends.
11. **Credential source → launcher.** The model key is read once, from the environment or 1Password, and held only in the launcher's memory. Every child process (`git`, the runtime CLIs, `op`) runs with every model credential variable removed and never gets the key as an argument or file. A GitHub token in the launcher's env refuses the run.
12. **Runner → deep-scan job (CI).** On the GitHub runner the agent and target run together in a gVisor container; the runner holds the launcher, its proxies and the delivery steps. The runner's Docker also runs the relay containers and their `-host` bridge network under Docker's default runtime (runc), not gVisor, and the probe containers under gVisor, as the sandbox; they run launcher code only (the pinned `node` image and the digest-checked relay script), never target code. Only the deep-scan step's env holds the model key; the job token and the advisory token never do. The job runs only from `schedule` or `workflow_dispatch` on the default branch, delivers the report after teardown through scripts staged and digest-checked beforehand, and prints nothing the scan shaped.

## Attack paths to walk

- **Prompt injection** via issue body, comments, PR diff, or file contents that makes the agent: run a denied tool, write outside the workspace, print findings to stdout, open a non-draft PR, or approve/merge.
- **Self-modifying PR**: a PR that edits a reusable workflow, prompt, skill, `CLAUDE.md`, `.claude/`, or the hook so its own review/audit runs weakened instructions.
- **Token exposure**: any secret reachable from an agent step's env, `.git/config` (`persist-credentials`), gh config dir, or a file the agent can read.
- **Staged-script bypass**: workspace copy of a credentialed script executed instead of the staged, digest-checked copy.
- **Tool grant widening**: `extra_allowed_tools` grammar escape, Bash prefix rules that admit writes (`--output=`), `Bash(gh:*)`.
- **Expression injection**: `${{ }}` interpolating attacker-influenced values directly into `run:` scripts.
- **Trigger loops / privilege mix-ups**: label not consumed, `pull_request_target` introduced, fork PRs receiving secrets, allowlist bypass.
- **Supply chain**: third-party actions not pinned by SHA; mutable Docker tags; Companion skills pulled unpinned into the runtime.
- **Public-log rule breach**: report fields echoed without closed-pattern validation; artifacts uploaded; counts comment carrying detail.
- **Sandbox escape or runtime downgrade**: a target or agent that reaches the host kernel, a host folder or the Docker socket; a runtime check fooled into accepting plain Docker on Linux, Docker Desktop's WSL 2 backend, Docker Desktop on macOS or a Docker Engine older than 28.0; a sandbox network the host has an address on, or a relay that forwards more than one port; a check trusted from inside the sandbox; a flag, setting or variable that lets a refused runtime through.
- **Host-side template build on Docker Sandboxes**: before `sbx template load`, the launcher pulls the recipe's `image` and builds its fixed layer (the pinned Claude Code, installed with npm, and the `agent` user) with `docker build` on the host's Docker Desktop, outside the sbx microVM, so a poisoned image or a step that runs there reaches Docker Desktop's VM. Limited by the layer being the launcher's own, which installs nothing beyond the pinned Claude Code and checks the image's tools rather than fetching them; by `dockerfile` recipes being refused on sbx, so no recipe `RUN` step runs there; and by the target and the agent running only in the microVM.
- **Copy-in widening**: the working tree, an uncommitted or untracked file, a pull request head, a committed `.env`, a GitHub token, SSH key or cloud config reaching the sandbox; a mount in place of a copy; a recipe, Dockerfile or `grounding` path read from anywhere but the default branch.
- **Setup egress bypass**: a setup step reaching a host outside `registries`; a `registries` entry or a non-deny-all sbx global policy admitting more; the egress proxy or the setup relay still reachable after the cut, or the cut checked from inside the sandbox.
- **Model proxy abuse**: a request forwarded to another host, through a `CONNECT` tunnel, on a dot-segment, batch or legacy path, to any endpoint or method but the Messages API's own `POST`, from a caller without the run's caller key, or with the sandbox's own auth headers; a body forwarded with a server-side tool, `mcp_servers`, a `container` or content naming a URL or file for the model API to fetch (the API itself would then reach outside the sandbox); requests sent together passing the cap check before any answer is counted; the real key echoed into the sandbox in an answer or error; the route left open after the agent step; a repository's `.claude/settings.json` that repoints the sandboxed Claude Code or turns its web tools back on.
- **Discovered instructions on the subscription path**: without `--bare`, the sandboxed Claude Code can load the scanned repository's `CLAUDE.md` files and skills, prompt-injection input that steers the scan or its report. Limited by the brief, which marks them as content under audit and says its own procedure decides; by settings still pinned (`--setting-sources user`, `--strict-mcp-config`, `disableAllHooks`), so they cannot repoint the base URL, start an MCP server or run a hook; and by the sandbox, which never holds the real token.
- **Credential leak from the launcher**: the key in a child process's env or arguments, on disk, or in a usage error or log line; `--credential-from` given the key itself; an unresolved `op://` reference or a GitHub token variable taken as the key.
- **Recipe steering**: a recipe change that raises a limit, starts a sibling container, mounts `docker.sock`, carries a real credential, or points probing at a deployed or third-party system; a `grounding` URL that makes the host fetch from somewhere the sandbox could not reach (limited to public `https://` hosts by DNS name, with no redirect followed and each resolved address checked and pinned).
- **Limit or teardown failure**: a wall clock, turn or token limit the agent can lift from inside (a second Claude Code started from Bash escapes `--max-turns`, so the wall clocks and the token cap are the hard bounds); a sandbox, network, sbx policy rule or layered image left behind after a failed step, a limit stop or an interrupt.
- **Copy-out widening**: a folder, link, second or oversized file taken as the report; the transcript, shell history, app logs or scratch scripts leaving the sandbox; a payload, exact request or command sequence in the report or draft advisory; an agent-written `Stopped:` line kept.
- **Verification run misuse**: a `--ref` that is someone else's pull request head, or an unreviewed private-fork branch; a recipe, skill or Threat pack read from the `--ref` instead of the default branch; the finding file, which names a concept id private until release, readable by a setup step, kept in the repository, printed, or accepted in GitHub Actions; a Verification-run report filed, posted or written to a `--report` path.
- **Process allowlist widening**: `init`, `upgrade` or `doctor` reaching a runtime CLI or `op`; a second runner that bypasses the allowlist; a shell between the launcher and a command.
- **Deep scan in a public log**: Claude Code's error output, the model proxy's refused hosts, paths or answer counts, the model ids the API answered with (anything in the sandbox can ask the proxy for a model of its choosing), the publisher's counts, or an artifact, cache or job summary in a public Actions log; a CI deep scan run on a pull request head or a ref other than the default branch.

## Out of scope

- Consumer product code and Consumer Threat packs.
- The Copilot archive while inert (not under `.github/workflows/`).
- GitHub platform and Anthropic service vulnerabilities, and those of the accepted sandbox runtimes and the 1Password CLI themselves.
