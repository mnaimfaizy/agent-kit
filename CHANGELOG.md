# Changelog

All notable changes to this project will be documented in this file.

The format is based on Keep a Changelog, and this project follows Semantic Versioning.

## [Unreleased]

### Added

- `security-response` keeps a **Security Response Run** ([#348](https://github.com/mnaimfaizy/agent-kit/issues/348), part of [#344](https://github.com/mnaimfaizy/agent-kit/issues/344)): a private local board that tracks a maintainer's response to every open draft advisory and is resumed by a later session. Every mode now opens the run when draft advisories exist and none is open, resumes the open run otherwise (at most one is open), and with no drafts and no open run reports "nothing to respond to" and writes nothing. The run lives in `tmp/security-response/<date>/` (`.2`, `.3` when taken), with no config key; before the first write the skill checks the path with `git check-ignore`, offers the `.gitignore` line when it is not ignored, and writes nothing without a yes. It holds `board.md`, an append-only `activity.md`, `triage/<concept-id>.md` and `originals/<GHSA-id>.json`, each advisory saved there before any PATCH that rewrites it publicly. Each `GHSA:F<n>` gets a provisional concept id from its title, and findings with the same id fold into one row. `status` prints the board: Waiting on you, Next (agent), a findings table and an advisories table. The new run doc `RUN.md` defines the board and the Evidence (`untriaged`, `confirmed`, `rejected`, `duplicate`, `below-floor`), Delivery (`open`, `fix PR open`, `merged`, `released`, `fixed`, `accepted-risk`) and advisory states, and what is final. The `argument-hint` gains `record <what>` and `close`, not available yet. **Consumer action:** add `tmp/security-response/` to your `.gitignore`, or say yes when the skill offers it.

- `security-response` reconciles its Security Response Run as step one of every mode ([#349](https://github.com/mnaimfaizy/agent-kit/issues/349), part of [#344](https://github.com/mnaimfaizy/agent-kit/issues/344)), so a later session resumes from the sources as they are now and the header's `checked <time>` updates each time. `RUN.md` gains the source table: the advisory list, state and CVE id from the advisory API, `fix PR open` from the private fork until publish deletes it, `merged` from the fix SHA being an ancestor of `origin/main` after a fetch, `released` from the tag containing it, `fixed` through the API where it can, and the findings ledger read only. The source wins for the facts it owns; the board wins for Evidence, fork PR numbers and fix SHAs once the fork is gone, a CVE request and accepted-risk. `merged` and `released` move on their own once verified, and judgements never do. An unreachable source reads `not checked: <source> unavailable` and moves no row. Final rows and advisories are not checked again, and a contradicted one stays final and goes to the top of Waiting on you. Reconcile never deletes a row: a new draft or a new `F<n>` joins as `untriaged`, and a missing `F<n>` keeps its row and is raised in Waiting on you. Each correction is logged in `activity.md` as `reconciled: <old> → <new>, checked <how>`. **Consumer action:** none.

- `security-response triage <target>` lands the `security-finding-triage` outcome on the Security Response Run's board ([#350](https://github.com/mnaimfaizy/agent-kit/issues/350), part of [#344](https://github.com/mnaimfaizy/agent-kit/issues/344)), so each judgement is kept with its reasons. The output is saved verbatim to `triage/<concept-id>.md`, the concept id becomes final, the Outcome maps to Evidence and Severity (after triage) to Severity. A same-concept finding is kept as a `duplicate` row with Record `of <canonical id>`. An `accepted-risk` outcome is only a recommendation in Waiting on you until the human records it. A finding found in triage enters as a new `untriaged` row with advisory `none yet`, and one confirmed at Medium or above needs a draft advisory before `fix PR open`. A standalone `security-finding-triage` run is not picked up. **Consumer action:** none.

- `security-response record <what>` lands the human's steps on the Security Response Run ([#351](https://github.com/mnaimfaizy/agent-kit/issues/351), part of [#344](https://github.com/mnaimfaizy/agent-kit/issues/344)), from a closed set: `merged <fix PR>` (a private-fork pull request, or a `below-floor` row's public one), `released <tag>`, `fixed <concept-id>: <how>`, `accepted-risk <concept-id>: <reason>`, `approve publish|close|cve <GHSA…>`, `match <GHSA> <concept-id>` and `ack <concept-id|GHSA>`. Anything else is refused with the list shown. `merged` and `released` run reconcile's checks (the fix SHA on `main`, the tag containing it) and move nothing on the report alone; `match` joins a human-made draft that names no concept id to a found-in-triage row; `ack` clears a contradicted-final entry from Waiting on you. Each transition leaves its record in the row's Record, and `activity.md` logs each `record` as a human report with what was verified. After `record approve`, the run publishes, closes or requests a CVE through `gh api`: publish is refused while any row under the advisory is not final, a duplicate advisory, or one whose every row is `rejected`, `duplicate` or `below-floor`, is closed rather than published, a duplicate once its canonical row's advisory is final, a CVE is requested only after a row under the advisory is `confirmed` and the request is recorded, and fork PR numbers and fix SHAs are recorded before publish deletes the fork. A row folded from two advisories is published, and gets a CVE, only through its canonical advisory, the earliest created: the other advisory publishes only its own rows, once the folded finding is removed from its body, or is closed like a duplicate advisory. **Consumer action:** none.

- `security-response` shows draft advisories with no findings on the Security Response Run's board and closes them by name ([#352](https://github.com/mnaimfaizy/agent-kit/issues/352), part of [#344](https://github.com/mnaimfaizy/agent-kit/issues/344)), so a clean audit's draft gets read and closed rather than forgotten. A draft with zero parsed `F<n>` is one advisories line with Rows `0 (<kind>)`, never a finding row. Its kind comes from the title CI gives it: `clean run`, `format mismatch`, `failed run`, or `other` for anything else, each with its own Next, and Waiting on you holds one item per kind, format mismatches and failed runs before clean runs. `record approve close <GHSA…>` takes an explicit list with no wildcard, a no-findings draft's only final state is `closed`, closing one writes no ledger line, and a run holding only no-findings drafts opens like any other. A `below-floor` row now keeps the advisory it came from (the ledger still writes `n/a` for it at close), so an advisory whose findings all fell under the Medium floor can be closed once its rows are final, instead of being refused for having no rows. A `below-floor` row still does not hold its advisory's publish. **Consumer action:** none.

- `security-response close` writes the findings ledger and closes the Security Response Run ([#353](https://github.com/mnaimfaizy/agent-kit/issues/353), part of [#344](https://github.com/mnaimfaizy/agent-kit/issues/344)), so the ledger moves once, when the response is done. `next` recommends `close` once every row and every advisory is final, and `close` checks again and refuses with the list of anything that is not. It previews the exact ledger lines, lets the human edit their Notes, and writes nothing without a yes. It then opens one ledger PR per run, on `chore/security-ledger-<run>` with one commit and never a direct push, which the human merges. The header reads `Closing: ledger PR #n` and Waiting on you holds only the merge, drafts that appear meanwhile wait for the next run, and reconcile marks the run `closed` once the pull request is merged and its lines are on `main`. A run with no ledger lines closes with no pull request. Each row becomes one line: its final concept id; Status `rejected` for `rejected` and `duplicate`, otherwise `released <tag>`, `fixed` or `accepted-risk`; First seen the advisory's created date, or the triage date for a finding found in triage; the full GHSA id of the row's canonical advisory, or `n/a` for a below-floor row or a row with no advisory; and Notes from triage's Proposed ledger row plus the public parts of the Record, never a fork PR number or clone path. Lines are appended in first-seen order, then by advisory, `F<n>` and concept id, no existing line is edited, a duplicate of a concept id already in the ledger adds none, and the ledger format is unchanged. The ledger is the Caller's `findings_ledger_path`, otherwise `.security/findings-ledger.md`. A closed run stays on disk, read-only, with `Closed <date>, ledger PR #n` in its header, and is the human's to delete. **Consumer action:** none.

- `security-audit` gains a third mode, `deep`, as skill text ([#366](https://github.com/mnaimfaizy/agent-kit/issues/366), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0016](docs/adr/0016-security-pocs-are-never-delivered-rather-than-never-produced.md), [ADR 0017](docs/adr/0017-deep-scan-is-a-security-audit-mode-not-its-own-skill.md)). Its sandbox procedure is the new `DEEP.md`, read only in `deep` mode: it refuses to scan from the host and points to the `agent-kit deep-scan` launcher, runs the `full` walk, attempts a Reproduction of each candidate, probes further only against the Scan recipe's entry points, writes the report early, and never uses web tools. Every mode gains the "never deliver" contract rule: nothing runnable goes into the report or the draft advisory, not even privately. `report-format.md` gains, for `deep` only, `Reproduced: yes | no | not attempted`, a prose Observation, the ledger reopen and regression marks, `### Open questions`, the launcher-written `Stopped:` header line and the Verification-run variant; severity and the Medium floor are unchanged. `security-finding-triage` reads `Reproduced` and the Observation as evidence and stays static. [docs/security-audit.md](docs/security-audit.md#deep-mode) describes the mode and what a deep report never contains. `full` and `pr` are unchanged. **Consumer action:** none.
- `agent-kit deep-scan` starts the Deep scan launcher with its first stage: it reads and validates the **Scan recipe** ([#367](https://github.com/mnaimfaizy/agent-kit/issues/367), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362)). The recipe lives at `.security/scan-recipe.yml` (or `--recipe <path>`) and is read as committed on the default branch (`--default-branch <b>` names it when origin's HEAD is not set), never from the working tree. It names an `image` or a `dockerfile`, `setup`, `registries`, `start` and `ready` (optional when every entry point is a command), an optional `seed`, `entry_points` each with a one-line note, `fixtures` with fake values, optional `grounding`, and `notes`. Limits, compose files, sibling containers, the Docker socket, real-looking credentials and unknown keys are refused. With no recipe or an invalid one, `deep-scan` lists every problem, points to the [recipe format](docs/security-audit.md#scan-recipe) and exits 1, with no fallback to `full`; a valid recipe exits 0, as the later stages are not built yet. `doctor` gains a `Scan recipe` check: none passes, an invalid one warns. **Consumer action:** none; a static-only Consumer needs no recipe.
- `agent-kit deep-scan` chooses a sandbox runtime from the host, or refuses, and refuses a stray credential first ([#368](https://github.com/mnaimfaizy/agent-kit/issues/368), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0018](docs/adr/0018-a-deep-scan-runs-locally-by-default.md), [ADR 0019](docs/adr/0019-the-npm-cli-runs-deep-scans.md)). After the recipe, it refuses when `GH_TOKEN` or `GITHUB_TOKEN` is set in its environment, or when the default branch has a committed `.env` (or `.env.<name>`; templates such as `.env.example` are fine) that the copy-in would forward wholesale. Then it picks, from host-side checks only, Docker Sandboxes, then Kata or Firecracker (Linux), then gVisor (Linux), then Docker Desktop on macOS. Plain Docker on Linux, Docker Desktop on Windows with WSL 2, and anything else are refused, naming the accepted runtimes and the CI path, with no override flag. A chosen runtime exits 0 before anything is started; the sandbox stages are not built yet. The CLI's process allowlist widens for `deep-scan` alone to the runtimes' CLIs (`sbx`, `docker`, `runsc`, `kata-runtime`, `firecracker`); `init`, `upgrade` and `doctor` still run only `git` and `gh`. [docs/security-audit.md](docs/security-audit.md#sandbox-runtimes) lists the accepted and refused runtimes. **Consumer action:** none.
- `agent-kit deep-scan` runs the sandbox lifecycle on the chosen runtime, from image to teardown, with a stand-in agent step ([#369](https://github.com/mnaimfaizy/agent-kit/issues/369), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0018](docs/adr/0018-a-deep-scan-runs-locally-by-default.md)). It pulls the recipe's image or builds its Dockerfile from the default branch, and layers Claude Code 2.1.328 with the auto-updater off; starts the sandbox with no mount, host environment or Docker socket; copies in a `git archive` of the default branch's tip (never the working tree) and the grounding files, and nothing else; runs `setup`, `start`, `ready` and `seed` with no agent or model credential and egress only to `registries`, through a proxy on the host; cuts the network and checks it from the host; runs the stand-in agent step; copies out the single report file to a private folder; and removes the sandbox, network and images on success, failure and interrupt. A failing setup, start or ready step ends the run before the agent step and shows its output. The lifecycle runs on gVisor, Kata and Firecracker as Docker runtimes on Linux, on Docker Desktop on macOS, and on Docker Sandboxes, where it requires a deny-all global sbx network policy (read with `sbx policy ls --json`, never changed), creates the sandbox mountless from the recipe's `image` (a `dockerfile` is refused), installs Claude Code inside it, and limits setup egress with per-sandbox `sbx policy` rules. [docs/security-audit.md](docs/security-audit.md#what-goes-into-and-out-of-the-sandbox) says what goes into and out of the sandbox. **Consumer action:** none; the image named or built by your recipe needs Node.js and npm, and on Docker Sandboxes run `sbx policy init deny-all` once before your first Deep scan.
- `agent-kit deep-scan` runs a real local Deep scan: the real Claude Code replaces the stand-in agent step, behind a key-injecting model proxy, on the API-key path ([#370](https://github.com/mnaimfaizy/agent-kit/issues/370), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0018](docs/adr/0018-a-deep-scan-runs-locally-by-default.md), [ADR 0019](docs/adr/0019-the-npm-cli-runs-deep-scans.md)). The model proxy runs on your machine and is the scan's only route out: it forwards only the Messages API's `/v1/` paths to `api.anthropic.com`, refuses any other host, tunnel or path, strips `x-api-key` and `Authorization`, and inserts your key, which lives only in its memory. Inside the sandbox, Claude Code runs with `--bare`, a placeholder `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` pinned by the launcher's own `--settings` (project and local settings are not loaded), and no web tools, and is handed the security-audit skill's `DEEP.md`, `SKILL.md` and `report-format.md`, the Threat pack and the Scan recipe, read from the default branch, with the sandbox's paths. The key comes from `ANTHROPIC_API_KEY`, another variable (`--credential-from env:<NAME>`) or 1Password (`--credential-from op://…`, through `op read`, or `op run`); the 1Password CLI joins `deep-scan`'s process allowlist alone. The report's local private path is printed, and nothing is filed or posted. `security-audit`'s `DEEP.md` now says the grounding is at `/agent-kit/grounding` and the report goes to `/agent-kit/out/report.md`. [docs/security-audit.md](docs/security-audit.md#credentials) gains Credentials and Running a deep scan. **Consumer action:** to run a Deep scan, make an API key in a dedicated Anthropic Console workspace with its own spend limit, and keep the security-audit skill (with `DEEP.md`) and the Threat pack on your default branch.
- `agent-kit deep-scan` bounds every Deep scan from outside the sandbox, and a run a limit stops still delivers what it found ([#371](https://github.com/mnaimfaizy/agent-kit/issues/371), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0018](docs/adr/0018-a-deep-scan-runs-locally-by-default.md)). The limits, with their defaults and options: a setup wall clock (20 min, `--setup-minutes`) from the image step to the agent step, a scan wall clock (60 min, `--scan-minutes`) over the agent step, Claude Code's turn limit (200, `--max-turns`, passed on its command line), and a token cap for the run (5,000,000, `--max-tokens`), held by the model proxy, which counts the input, output, cache-creation and cache-read tokens in the model API's returned `usage` and refuses every request once the count reaches the cap. The proxy also refuses the batch and legacy completion paths, whose spend no answer shows. The Scan recipe still never sets a limit. A value that is not a positive number is a usage error (exit 2). A limit that fires stops the running step, copies out the report so far with the launcher's `- **Stopped:** wall clock | turns | tokens` line after `Finding count` (any `Stopped:` line the agent wrote is removed), tears the sandbox down and exits 3; a stop with no report writes no file and prints only `Stopped:` with the limit. [docs/security-audit.md](docs/security-audit.md#limits) gains Limits, with the backstops: the Console workspace spend limit, and on the subscription path the token cap as the only spend lever. **Consumer action:** none; raise a limit with its option when a scan of a large repository stops early.
- An opt-in CI path for the Deep scan: a new reusable workflow, `deep-scan-reusable.yml`, with a Caller example, `examples/deep-scan-caller.yml` ([#373](https://github.com/mnaimfaizy/agent-kit/issues/373), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0018](docs/adr/0018-a-deep-scan-runs-locally-by-default.md)). It runs the same `agent-kit deep-scan` on an ephemeral GitHub-hosted runner with gVisor (`runsc`, a pinned, SHA-512-checked release), on the default branch only (a schedule or `workflow_dispatch`, never a pull request head). Its inputs are the kill switch, the model and the limits; the model key is its own Caller secret, `anthropic_api_key`, in the launcher step alone, and the job token and the advisory token never reach it. The draft advisory and the optional email are delivered after teardown by the static audit's own scripts, staged from the trusted commit and digest-checked. Nothing from the scan is printed or uploaded, and the log keeps a status with no counts. The job's `timeout-minutes` is 180, and `setup_minutes` plus `scan_minutes` may be at most 150. `deep-scan` gains `--model <id>` and `--report <path>`, and in GitHub Actions (`GITHUB_ACTIONS=true`) withholds Claude Code's error output, the model proxy's refused hosts and answers, and copy-out error detail. `security-audit-reusable.yml` is unchanged. [docs/security-audit.md](docs/security-audit.md#deep-scan-in-ci) describes it. **Consumer action:** none; to adopt it, copy the Caller, add the `AGENT_KIT_DEEP_SCAN_ANTHROPIC_API_KEY` secret and set `CLAUDE_DEEP_SCAN_ENABLED` to `true`.
- `agent-kit deep-scan --verify <file> --ref <ref>` runs a **Verification run**: it re-attempts the Reproduction of known findings on a local ref you name, such as your fix branch, to check whether the fix holds ([#372](https://github.com/mnaimfaizy/agent-kit/issues/372), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362); [ADR 0018](docs/adr/0018-a-deep-scan-runs-locally-by-default.md)). The finding file is Markdown in a deep report's shape (each finding a `###` section with a Concept id, Location and Observation), checked on your machine before anything runs. The ref's committed tree is exported, never the working tree, while the recipe, the skill and the Threat pack still come from the default branch. The run is confirm-only: the agent gets the Verification-run procedure from `DEEP.md`, not the full deep procedure, and the finding file goes in with its brief after the network cut. Its defaults are a 15 min scan wall clock, 50 turns and the same token cap. The report, in the Verification-run variant, goes only to a new private folder; `deep-scan` prints each finding's `Reproduced: yes` (the fix does not hold) or `no` (it holds), and files or posts nothing. `--verify` is refused in GitHub Actions, and is a usage error with `--report` or without `--ref`. See [Verification run](docs/security-audit.md#verification-run). **Consumer action:** none.
- `agent-kit deep-scan` refuses a Claude subscription token used as the model credential, before any runtime starts and without printing it: a key that starts with `sk-ant-oat`, from any source, or `--credential-from env:CLAUDE_CODE_OAUTH_TOKEN` (part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362)). It used to be sent as the API key and end in a 401 once the sandbox was built. Without the opt-in, `--credential subscription` ([#375](https://github.com/mnaimfaizy/agent-kit/issues/375)), it now points to it; see [Credentials](docs/security-audit.md#credentials). **Consumer action:** none; use an Anthropic API key, or opt in.
- `agent-kit deep-scan --credential subscription` runs a Deep scan on a Claude subscription token, an opt-in at your own risk ([#375](https://github.com/mnaimfaizy/agent-kit/issues/375), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362)). The token comes from `CLAUDE_CODE_OAUTH_TOKEN` (or `--credential-from env:<NAME>` or `op://`), stays in the model proxy, and is sent as the `Authorization: Bearer` value only; the sandbox holds a placeholder, and Claude Code runs without `--bare` (with `--strict-mcp-config`, `ANTHROPIC_BASE_URL` still pinned by the launcher's settings, and a brief that marks the repository's discovered `CLAUDE.md` and skills as content, not instructions). The deep-scan workflow takes it as an optional `claude_code_oauth_token` secret, the alternative to `anthropic_api_key`, which is no longer required: exactly one must be set. It relies on undocumented behaviour and may break with any Claude Code release, has no refresh (rotate it by hand), leaves the terms question to you, and the proxy's token cap is its only spend lever. It passed its acceptance check, a real run, on 2026-11-20 (Claude Code 2.1.328, Docker Sandboxes v0.54.0). A subscription token without the flag is still refused, now pointing to it, and an API key with it is refused. **Consumer action:** none; to opt in, see [the subscription path](docs/security-audit.md#the-subscription-path-opt-in).
- `agent-kit deep-scan --effort <level>` chooses the agent's effort level, and a run names what scanned your code (part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362), user story 58a). `--effort` takes `low`, `medium`, `high`, `xhigh` or `max`, the values of Claude Code's own `--effort` and of the static workflow's `effort` input, and passes it on to Claude Code on either credential path and in a Verification run; anything else is a usage error (exit 2) before any runtime starts, and without it Claude Code's default applies. `deep-scan-reusable.yml` gains an `effort` input with the static workflow's description and check (empty leaves `--effort` off), and the Caller example reads `CLAUDE_DEEP_SCAN_EFFORT`, then `CLAUDE_EFFORT`. The `Agent step:` line now names the requested model and effort, or `Claude Code's default` for each, and the `Model proxy:` line names the model id (or ids) the API answered with, read from each answer's `model` field. In GitHub Actions the requested model and effort still print, but the answered model ids are withheld under the Public-log rule, since anything in the sandbox can call the proxy with a model of its choosing. **Consumer action:** none; to set the deep scan's effort in CI, add `effort: ${{ vars.CLAUDE_DEEP_SCAN_EFFORT || vars.CLAUDE_EFFORT || '' }}` to your deep-scan Caller.
- `agent-kit deep-scan` on Docker Sandboxes starts a sandbox again: `sbx create -t <recipe image> shell` could not start one, since sbx v0.54.0 writes `/home/agent/AGENTS.md` as a sandbox starts and a plain image has no `/home/agent` ([#375](https://github.com/mnaimfaizy/agent-kit/issues/375), part of [#362](https://github.com/mnaimfaizy/agent-kit/issues/362)). The launcher now builds the sandbox's template with Docker on the host: it pulls the recipe's `image`, layers on it the pinned Claude Code and a non-root `agent` user (uid 1000, home `/home/agent`, the image's `USER`; an existing uid 1000 user such as `node` is renamed), checks it has curl, git, CA certificates and bash (installing none), loads it with `sbx template load`, and creates the sandbox with `--pull never -t` from it; teardown removes the template and the layered image. Claude Code is no longer installed inside the sandbox, so its `registry.npmjs.org` setup step is gone. The model route's per-sandbox rule now names `localhost:<port>`, the name sbx's policy gives the sandbox's connection to `host.docker.internal:<port>`: the old rule never matched, so no model request got through. `dockerfile` recipes are still refused on sbx. Setup steps and the agent now run as that `agent` user on sbx. **Consumer action:** on Windows, install Docker Desktop beside Docker Sandboxes; it builds the template only, and the target still runs in the sbx microVM. A recipe image for sbx needs curl, git, CA certificates, bash and `useradd`/`usermod`, and its setup steps must not need root.

### Changed

- `security-response`'s `reconcile` mode now reconciles the Security Response Run against GitHub and git and does nothing else ([#349](https://github.com/mnaimfaizy/agent-kit/issues/349)); it no longer refreshes finding evidence against the current code, which is triage's work. **Consumer action:** none.
- `security-response`'s Delivery state `fixed; Release pending` is now `merged`, and `fixed` always means done with no release; Evidence gains `duplicate` and `below-floor` ([#348](https://github.com/mnaimfaizy/agent-kit/issues/348)). The glossary's **Concept id** is provisional until triage, and stable from then on. **Consumer action:** none.
- **Breaking:** `security-finding-triage` no longer edits the findings ledger ([#350](https://github.com/mnaimfaizy/agent-kit/issues/350)): its process step that updated the ledger is removed. Its outcome's "Ledger update" section is now "Proposed ledger row", in the ledger's five columns, which only a Security Response Run's `close` applies. The outcome format gains `below-floor` (real, but under the Medium floor) with a `low` severity, a `Duplicate of` line and a "Found in triage" section, and keeps `accepted-risk` as a recommendation mapped to the Delivery ending. **Consumer action:** if you ran `security-finding-triage` on its own to keep your ledger current, copy its Proposed ledger row into the ledger by hand.
- The findings-ledger skeleton in `examples/threat-pack/`, which `agent-kit init` copies, now says only a Security Response Run's `close` or the maintainer, by hand, writes the ledger ([#353](https://github.com/mnaimfaizy/agent-kit/issues/353)). It asks for the example row to be deleted by hand, since `close` only appends, and lists the Status values `close` writes: `released <tag>`, `fixed`, `accepted-risk` and `rejected`. Its header text and five columns are unchanged. **Consumer action:** none; your own copy is yours, and you may drop `open`, `confirmed` and `duplicate` from its Status values line.

### Removed

- `security-response`'s `STATUS-FORMAT.md` ([#348](https://github.com/mnaimfaizy/agent-kit/issues/348)): `status` prints the run's board, whose format is in the skill's `RUN.md`. **Consumer action:** none, unless you link the file; link `RUN.md` instead.

### Fixed

- `prepare-release.sh` no longer rewrites the `release:` field of [Deprecation register](docs/deprecations.yml) entries when it bumps the previous tag's pins ([#361](https://github.com/mnaimfaizy/agent-kit/issues/361)). That field is the release each rename shipped in, so the bump left the register claiming the previous release's renames shipped in the new one, and a re-run of `prepare` could list them in the new release's notes. On [#268](https://github.com/mnaimfaizy/agent-kit/pull/268) a bulleted list of confirmations under `## Spec` failed the Review report check, because every list item there must link a thread.
- On re-review, the kit's reviewer brief says what to do with an unanswered thread whose finding the head has fixed: leave it out of the Review report's lists and say so in one sentence of prose. Before, it said only to list such a thread "if it still applies". On [#276](https://github.com/mnaimfaizy/agent-kit/pull/276) the second review listed its seven fixed findings as list items without thread links, and the Review report check failed the job.
- What the kit's reviewer checked and found fine now has a place in the Review report: below a `### Checked` line at the end of its axis, as a list or prose. The Review report check skips list items there; every other list item under the three axis headings must still link a thread. The brief rule to write those notes as prose did not hold: on [#283](https://github.com/mnaimfaizy/agent-kit/pull/283) the first review posted seven threads, then listed eight checked notes under `## Standards` and `## Correctness`, and the check failed the job. **Consumer action:** copy `.github/agent-runtime/review-threads.mjs` from the same tag as the workflow pin (`agent-kit upgrade` does it). Without the new script, a review that uses `### Checked` fails as before.
- Review response's staged `verify.sh` (and `format.sh`) now end with one line giving the exit code and the last command that failed (with errtrace, so a failure inside a function is named too), or `exited 0`. The Caller's commands run in a child shell, so a trap they set cannot remove that line. The agent sees a long check output cut short, and on [#254](https://github.com/mnaimfaizy/agent-kit/pull/254) it could not tell which check broke. The dogfood Caller also uses quiet reporters.
- Review response's `verify_commands` run inside Claude Code's sandbox, which allows writes only to the working tree and a temp directory, with no network. `uv run` fails there with exit 2, because it cannot create its cache under `~/.cache`, so the round on [#254](https://github.com/mnaimfaizy/agent-kit/pull/254) could only decline. The dogfood Caller now calls `.venv/bin/pytest` and `.venv/bin/ruff` directly, and [review-response.md](docs/review-response.md) and the example Caller say to call installed tools, not cache-writing wrappers.
- Review response no longer fails every round at **Check git configuration after setup**. That step refuses `GIT_*` variables that setup could leave to steer git, but the step itself was given the trusted git's path as `GIT_BIN`, so the check matched its own input and stopped each round before the agent ran (seen on [#254](https://github.com/mnaimfaizy/agent-kit/pull/254)). The variable is now `TRUSTED_GIT`, and a contract test runs the check with the step's own environment. Affects v1.0.0-beta.7.

- `manual-qa` runs each fix scenario at the merge-base too, and grades every scenario with one of five results under one of three headlines ([#234](https://github.com/mnaimfaizy/agent-kit/issues/234), part of [#231](https://github.com/mnaimfaizy/agent-kit/issues/231)). Before, every scenario ran once, at the head, as PASS, FAIL or _left for a person_, so a fix scenario could pass at the head without the run ever seeing the defect it fixes. On a `stack` target with at least one scenario carrying **Expected before:**, step 5 now runs a Before pass first: a detached `git worktree` of the plan's merge-base under `working_dir`, `up`, `migrate` and `seed` there (processes recorded in their own `stack-pids-before.txt`), the fix scenarios only, compared with **Expected before:**, then `down`, the recorded processes stopped, and the worktree removed, on failure too. Only then does the head stack start as before, so the two stacks are never up at once and the database is only migrated forward. A Before that cannot start, or a step the merge-base does not match, makes that scenario's Before _not observed_ and never stops the head run. It asks before writing (`--yes` skips the question and is required without a terminal), writes only local files, and commits nothing; where `core.fileMode` is off (Windows), it stages each copied file with the tag's mode (adding or removing the executable bit), and `doctor` now takes a file's mode from the index there, as git does. `doctor`'s fix command for stale Kit-owned paths now names a CLI version that has `upgrade`. It writes the Threat pack skeleton to `.security/` (or `--threat-pack-dir`, which also updates the audit Caller's paths) and `.github/dependabot.yml` when there is none. It prints the secrets, labels, Claude GitHub App, rulesets and Kill switch steps as `gh` commands. Every answer is a flag or a question; `--yes` asks nothing. It refuses to overwrite an existing Caller or Kit-owned path without `--force` (which lists the uncommitted changes it would discard), never overwrites an existing Threat pack file, and leaves Kit-owned paths that already match the tag alone, so a second flow can be added later. See [Getting started](docs/getting-started.md#adopt-with-the-cli).
- Threat pack skeletons in `examples/threat-pack/` (`threat-model.md`, `findings-ledger.md`), shaped after what the `security-audit` and `security-finding-triage` skills read and write. Copy them by hand or let `init` do it; the copies are yours.

### Changed

- The example Callers are named `agent-pipeline` and `security-audit` (their `name:` lines), matching the files `init` writes. A contract test holds each example to the placeholders `init` fills in.
- `doctor` and the new commands now print invisible and bidirectional formatting characters (zero-width characters, LRM/RLM, embeddings, overrides, isolates and the byte-order mark) as `\uXXXX`, as they already did for control characters, so a file name or message cannot read differently from what it is.

### Fixed

- A scheduled audit could fail with "Empty report" when the agent started a background subagent and ended its turn waiting for it, which ends a headless run ([#92](https://github.com/mnaimfaizy/agent-kit/issues/92)). The plan, implement and audit steps now set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, as review already did, so subagents and commands run only in the foreground. All four agents also deny `ScheduleWakeup`, `CronCreate`, `RemoteTrigger` and `SendMessage`, which need no permission, and `Workflow`, `Monitor` and `PushNotification`, which start background work or reach outside the run; no run uses any of them. The planner and the auditor also deny `Agent`, and the audit prompt says to finish in one turn. Review still runs its axes as parallel foreground subagents. One side effect for the implementer: a Bash command that reaches its timeout (2 minutes unless the agent sets a longer one, up to 10) now stops instead of carrying on in the background, so a test command granted through `extra_allowed_tools` that runs longer than that fails in the agent's session. The verify step after the agent is unaffected. No inputs, secrets or permissions changed.
- When an implement run failed before the agent started, for example because `setup_commands` failed, the "Check git configuration after the agent" step blamed the agent with "The agent run left git configuration or hooks outside the allowlist" and a `MODULE_NOT_FOUND` error ([#83](https://github.com/mnaimfaizy/agent-kit/issues/83)). The check now runs only when the hooks were staged. It still runs after a failed agent step: the agent can only start after staging succeeds, so any run in which the agent started is still checked.
- The plan, implement, review and audit runs no longer fail when GitHub's release CDN returns 5xx on the Bun download ([#86](https://github.com/mnaimfaizy/agent-kit/issues/86)). Each reusable workflow now installs the Bun version the pinned `claude-code-action` expects (1.3.14) before the action runs. It downloads from the npm registry first and falls back to the GitHub release through `api.github.com`, retrying each source for a few minutes. If neither source works, the job fails with "Bun install failed" instead of a later `bun: command not found`. No inputs, secrets or permissions changed.
