# The Review responder's agent holds no write credential; a separate job pushes and speaks for it

The Review response flow (`agent-review-response-reusable.yml`, [#129](https://github.com/mnaimfaizy/agent-kit/issues/129)) runs the `address-pr-review` skill unattended on a pull request: the Review responder fixes, addresses or declines each Finding. To prove a fix it has to build the pull request's code, so whatever runs in its job can be reached by the pull request's own dependencies and build scripts. That job is therefore given nothing worth taking: a read-only job token and no `id-token` grant. The agent commits locally, and its commits leave the runner as a git bundle. A `publish` job, on a fresh runner with only the default branch's code checked out, validates the bundle, pushes it with the job token, starts the one CI run GitHub holds for such a push, and replies on and resolves the review threads. The kit's other agents keep their credentials: only the implementer holds the Claude GitHub App token, and it builds the default branch, not a pull request.

This restates Issuebridge's [ADR 0006](https://github.com/mnaimfaizy/issuebridge/blob/main/docs/adr/0006-review-responder-holds-no-write-credential.md), where the design was built and audited, for the kit. The three jobs are kept whole:

- **gate** reads the pull request live from the API and records its head sha and the trusted sha (the default branch's tip, read live). It holds `pull-requests: write` only, to consume the Trigger label and say why it refused, and checks nothing out.
- **respond** holds `contents: read` and `pull-requests: read`. It reads the trusted script, the skill and the confinement hooks from the trusted commit's objects, never the working tree, and builds the Work list and the brief before any pull request code runs. Install scripts are off, and the agent's commands run in the bubblewrap sandbox with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, all fixed by the kit. The agent may edit, run the Caller's checks, `git add` and `git commit`: no push, no `gh`, no reads of `.git/`.
- **publish** holds `contents: write`, `pull-requests: write` and `actions: write`, and runs only trusted code.

## Considered Options

- **Push from the agent's job as the Claude GitHub App, as `implement` does.** Rejected. `id-token: write` is a job-wide grant, so every step of that job, including the dependency install and each build of pull request code, could exchange it for a token that writes the repository. The implementer avoids this only because it builds the default branch.
- **Keep the App token and turn install scripts off.** Rejected. The agent's own builds still run dependency code beside the grant: it narrows the exposure without closing it.
- **Push with the job token and dispatch CI on the branch.** Rejected: checks from a `workflow_dispatch` run are recorded on the commit but do not appear in the pull request's checks and cannot satisfy a required check. A job-token push does create the ordinary `pull_request` run, held for approval. `publish` approves that run instead, only for the Caller's `ci_workflow` and only for the exact commit it pushed.
- **Hand the commits over as patches (`git format-patch` / `git am`).** Rejected. Applying a patch writes a working tree from attacker-written text and changes every commit id, so the agent's "fixed in <sha>" claims could no longer be checked. A bundle is fetched as objects, fsck'd on the way in, never checked out, and keeps the ids.
- **Let the agent reply and resolve itself with `gh`.** Rejected. `gh api` also reaches merging, branch deletion and labels, and the agent could resolve threads it was never given.
- **A reusable workflow for auto mode.** Rejected. A Handoff (a finished review starting a round) by a reusable workflow would make the review workflow hold the responder's permissions. Auto mode ([#130](https://github.com/mnaimfaizy/agent-kit/issues/130)) dispatches the responder from the review workflow's own job instead.
- **A review ↔ respond loop.** Rejected. Two agents from one model family converging on agreement is the failure to avoid. A Response round never starts a review, and auto mode stops after two rounds on a pull request.

## Consequences

- **`publish` trusts nothing from the agent's runner.** A round's commits are accepted only as a straight line of at most twenty ordinary commits on the commit the round started from, with no merge, symlink or submodule, touching no protected path, no workflow file and no path unsafe to check out on Windows. A `fixed` Verdict has to name a commit `publish` itself pushed, and the thread is resolved only if that commit changes the file the finding is on. The summary comment carries no agent-written text, because its author and marker are what the round cap counts.
- **Rounds are refused** on fork pull requests, on pull requests that do not target the default branch, on Dependabot's, and on pull requests that change a protected path. "Trusted code" means the default branch's, so a pull request into any other branch would make that branch's author the trust root.
- **A Caller must keep the runtime on its default branch.** The script (`.github/agent-review-response/`), the hooks (`.github/agent-runtime/`) and the skill (`.claude/skills/address-pr-review/`) are read from there, not from the kit tag the Caller pins.
- **What remains exposed is the subscription token.** The agent step has to hold it while pull request code builds. Install scripts are off and the subprocess environment scrub is on, but the scrub is best-effort by the action's own description. The Caller's setup runs pull request and dependency code on the same runner before the agent step, so whatever it leaves behind (a process still running, a changed binary, environment or `PATH` entries for later steps) can reach the token as well. The workflow refuses the plain cases before the agent starts: git config or hooks in the checkout, changed hooks, git and loader variables, a different `git`, a workspace directory on `PATH`. Those checks are defence in depth, not a boundary. That token can make model requests and nothing else, and is revoked by running `claude setup-token` again. The read-only job token is on the runner too; for a private repository it can read what the checkout already holds and the repository's issues and pull requests.
- **On the label path the Caller's workflow file comes from the pull request's merge commit**, as for every `pull_request` workflow: anyone able to push a same-repository branch can already run an edited Caller with its secrets. The kit's reusable workflow itself comes from the tag the Caller pins.
