# Why the Chief of Staff goes idle, and what keeps it checking

Research for the `orchestrate` skill ([SKILL.md](../../.claude/skills/orchestrate/SKILL.md) steps 5 to 7, [HARNESSES.md](../../.claude/skills/orchestrate/HARNESSES.md)): on Claude Code desktop and on Cursor, the Chief of Staff sometimes sits idle after a Delegation reports, while the human is away. This note says why, which mechanisms can wake a session without the human, and what the skill text should say instead of "end the turn. Never poll."

## 1. What the skill says today

- `await` on Claude Code desktop: "end the turn. The app continues the Chief of Staff when a started session ends a turn, quoting the start of its latest report. Never poll." ([claude-code-desktop.md](../../.claude/skills/orchestrate/harnesses/claude-code-desktop.md), Verbs).
- `await` on Cursor: "end the turn. A background sub-agent's end is announced with its final message. Never poll. If the editor does not announce it, read `~/.cursor/subagents/` at an interval matched to the work." Its check-before-use list already holds "That the editor, and not only the CLI, announces a background sub-agent's end." ([cursor.md](../../.claude/skills/orchestrate/harnesses/cursor.md)).
- Step 7's review wait: "Check it again at the pace the review takes, minutes apart: at each `await`, or with `gh run watch <run-id> --interval 60`" ([SKILL.md](../../.claude/skills/orchestrate/SKILL.md#the-review-workflow)).
- The Brief Contract says the Delegation "writes its report when it reaches a stop point" ([BRIEF.md](../../.claude/skills/orchestrate/BRIEF.md), item 8). Nothing says the report must be final before the turn ends, and nothing says how to signal that it is not.

So `await` rests on one event per Delegation, the harness's turn-end signal, and nothing re-arms a wait when that event does not come, or comes too early.

## 2. Claude Code desktop

### 2.1 Why the Chief of Staff goes idle

The app's continuation is narrower than the skill assumes. The `start_session` tool's `wake_when_done` parameter (**tool description**, 2026-11-18) reads: "Once this session (and any sibling still working) ends its turn, or fails to start (unless it waits at a prompt the user answers there, its folder was never opened in Claude Desktop, or the user started, stopped or archived it), and you are idle, the app continues you, whether or not this is set." From that text, six causes, which add to the three seen in the run:

1. **(a) The wake fires on a turn end, not on a final report.** The app continues the Chief of Staff when the Delegation _ends a turn_. A Delegation that ends its turn while its own background command still runs ("I'll write the report when it finishes") wakes the Chief of Staff with nothing to verify. A background command started by the main conversation keeps running after the turn ends ([tools-reference, "When a background command stops"](https://code.claude.com/docs/en/tools-reference.md#when-a-background-command-stops)), and its exit starts a new turn in the Delegation ([goal, "Background work defers evaluation"](https://code.claude.com/docs/en/goal.md#background-work-defers-evaluation): "When the background work finishes, Claude Code delivers the result to Claude as a new turn"). Whether the app continues the Chief of Staff again when that _second_ turn ends is not stated: the tool text says "Once", and the run saw no second wake (**observed in run**). **UNCONFIRMED** (1).
2. **"And any sibling still working".** With two Delegations running, the reading is that the Chief of Staff is continued only once every working sibling has ended its turn. A report from a short Delegation then waits behind a long one. **UNCONFIRMED** (2) whether "sibling" means every session this one started, or only those started together.
3. **"Unless it waits at a prompt the user answers there".** A Delegation stopped on a permission prompt does not wake the Chief of Staff. With the human away, that is a silent stall: nothing reports it.
4. **"And you are idle".** A Chief of Staff busy in a long turn (a `gh run watch` in the foreground) is continued only after that turn ends; this is by design, but it delays the relay.
5. **(b) Waits on state the app cannot see.** CI, a review workflow run, a label: no app event covers them. A background Bash command does start a new turn when it exits ([goal](https://code.claude.com/docs/en/goal.md#background-work-defers-evaluation)), and a local desktop session puts no time limit on background commands ([tools-reference, "Time limit for background commands"](https://code.claude.com/docs/en/tools-reference.md#time-limit-for-background-commands)). But a wait loop with its own cap that exits with nothing found starts one turn, and if that turn ends without starting another wait, nothing re-arms. A `Monitor` watch ends at its deadline (5 minutes by default, at most 30) with "one notice, so it can start the watch again" ([tools-reference, Monitor tool](https://code.claude.com/docs/en/tools-reference.md#monitor-tool)): the re-arm is the model's job.
6. **(c) Cross-session messages can be held, not delivered.** In the desktop app's own messaging surface, "If the receiving session is mid-task, Claude Code holds the message and Claude reads it once the current work finishes" ([desktop, "Work across sessions"](https://code.claude.com/docs/en/desktop.md#work-across-sessions)). With no `crossSessionInbound` set, Claude Code decides by permission-mode class: a session that bypasses permission prompts holds every message from a session that does not, and a session that prompts holds a message from one that bypasses. "A session in the VS Code extension or the Desktop app can't show the dialog": a held message waits for `dialogExpiry` (five minutes by default) and is then dropped ([cross-session-messaging, "Control inbound messages"](https://code.claude.com/docs/en/cross-session-messaging.md#control-inbound-messages)). So a Chief of Staff in Bypass permissions and a Delegation in Auto (or the reverse) lose each other's messages unattended. `SendMessage` also warns that "for a Remote Control, cloud or Claude Desktop session nothing reports back, so never treat silence as agreement" (**tool description**). Whether a message that lands at the instant the Chief of Staff's own turn ends starts a new turn is **UNCONFIRMED** (3); the docs say an idle receiver gets a new turn ([cross-session-messaging, "Message delivery"](https://code.claude.com/docs/en/cross-session-messaging.md#message-delivery)).
7. **The machine sleeps.** `request_keep_awake` (**tool description**): "By default the app already does this through each turn"; `until: "session_idle"` "lets go once the session has been idle for about 5 minutes", and "a closed lid still sleeps". A Chief of Staff idle while CI runs lets the machine idle-sleep, and every local timer below stops with it.

Of the run's three shapes, (a) and (b) are what the harness does by design; (c) is the permission-mode hold, or a delivery race. Causes 2, 3 and 7 are further ways the same silence happens.

**Backgrounded app, sleep, quit.** Session-scoped tasks need the Claude Code process running and idle; closing the session stops them ([scheduled-tasks, Limitations](https://code.claude.com/docs/en/scheduled-tasks.md#limitations)). Desktop local scheduled tasks run "only while the desktop app is running and your computer is awake"; **Keep computer awake** in **Settings > Desktop app** prevents idle sleep, and a closed lid still sleeps ([desktop-scheduled-tasks, "How scheduled tasks run"](https://code.claude.com/docs/en/desktop-scheduled-tasks.md#how-scheduled-tasks-run)). That the app's window being in the background or minimised does not stop a session-scoped cron from firing is not stated: **UNCONFIRMED** (5), likely, since the session process keeps running.

**Cost.** Every wake is a turn on the Chief of Staff's model over its whole context. A `*/5` cron starts 15 seconds early so it lands inside the five-minute prompt cache; any other interval re-reads the context uncached ([scheduled-tasks, Jitter](https://code.claude.com/docs/en/scheduled-tasks.md#jitter)). Event mechanisms (`notify_when_idle`, a background command's exit) cost nothing until they fire.

**Can a session schedule its own wake-up outside `/loop`?** Yes, with `CronCreate`: a one-shot ("in 45 minutes, check whether…") or a recurring task, created by the model, which survives the turn end and fires when the session is idle ([scheduled-tasks, "Set a one-time reminder"](https://code.claude.com/docs/en/scheduled-tasks.md#set-a-one-time-reminder)). Not with `ScheduleWakeup`, which belongs to a self-paced `/loop`.

### 2.3 Does the maintainer's idea work here?

Yes, and the session already has the tools for both halves:

- **The reminder: `notify_when_idle`, re-armed on each wake.** After `spawn`, and again on every wake whose Delegation is not final, the Chief of Staff calls `SendMessage` with `to` the Delegation's `local_…` session id, `notify_when_idle: true`, and no `message` (a pure subscription that "costs that session nothing"). This closes shape (a): the notice comes when the Delegation next goes idle, after its background command and real report. It is one-shot, so re-arming it is part of handling each wake. It does not fire for a Delegation stuck on a permission prompt, since that session is not idle, and it is dropped after 12 hours.
- **The short-interval check: one recurring `CronCreate` heartbeat.** A cron task re-arms itself: it fires every interval until it is deleted or seven days pass, whatever the turns in between did. That makes it the fallback for (b), (c), the sibling wait and the stalled prompt. Its prompt is plain text (a `/orchestrate …` command in it would not run: the skill is `disable-model-invocation`). On each fire the Chief of Staff: reads the board; for each running Delegation, compares `report.md` and `decisions.md` against what it last handled (time and size), and reads the session's state with `get_session` / `list_events` where nothing new was written; checks each external wait (`gh pr checks`, `gh run list` for the review Caller); acts on anything new as step 6 says; re-arms any `notify_when_idle` or watch that has lapsed; and, when nothing changed, appends one line to the Activity Log and ends the turn at once. When the run reaches close-out, or parks waiting on the human's merges, it deletes the heartbeat with `CronDelete`.

Neither stops the machine sleeping. A run left unattended needs the human to turn on **Keep computer awake**, or to approve `request_keep_awake` with `until: "session_idle"`, which lets go after about 5 minutes idle, so it covers less than it seems. Changing the setting is the human's to do.

## 3. Cursor

### 3.1 Why the Chief of Staff goes idle

1. **The announcement itself is unproven in the editor.** The docs say only that a background subagent "Returns immediately. The subagent works independently" and that "Background subagents write output to `~/.cursor/subagents/`. The parent agent can read these files to check progress" ([Subagents](https://cursor.com/docs/subagents.md)). That a completion notice carries the final message is a CLI changelog entry (v2026.07.06), and the CLI had to restore it: "Background task follow-ups are back. Completion follow-ups for finished background tasks fire again in interactive and headless sessions" (v2026.08.11, [CLI changelog](https://cursor.com/docs/cli/changelog.md)). No editor doc or changelog says a finished background subagent starts a new turn in an _idle_ parent: **UNCONFIRMED** (6), and it is already a check-before-use item in [cursor.md](../../.claude/skills/orchestrate/harnesses/cursor.md). Staff on the 2.5 thread confirmed `is_background: true` did not make a subagent run in the background (Colin, 2026-02-28) and promised a fix in 2.6 (Colin, 2026-03-02) ([forum](https://forum.cursor.com/t/cursor-2-5-async-subagents/152125)); no staff post there covers waking an idle parent.
2. **(a)** applies as on desktop: the announcement, where there is one, is for the subagent's end, which may come before its report is final.
3. **(b)** applies, and harder: the editor documents no in-session scheduler and no idle wake for a background shell. The CLI has one in ACP mode only as of v2026.10.08 ("when the agent starts a background shell that watches for output, the prompt now stays open and the agent wakes up and responds whenever the output matches. Previously the agent said it would be notified, but the wakeup never arrived"). A QA Delegation run as `agent -p` in a background shell depends on the same unproven wake.
4. **(c)** has no direct counterpart: `message` to a sub-agent is "Resume agent `<id>`", once it has ended. A queued message in the editor "waits for the current task to finish" ([Agent overview](https://cursor.com/docs/agent/overview.md)).

### 3.3 Does the maintainer's idea work here?

The reminder does not: there is no tool for it. The short-interval check does, in one of two forms:

- **Keep the turn open (the reliable form).** `await` becomes a foreground watch the Chief of Staff runs and waits on: a shell loop that sleeps 60 seconds between checks and exits as soon as any Delegation's `report.md` or `decisions.md` changes, a file under `~/.cursor/subagents/` changes, or a pull request it is waiting on changes state, or after a cap (10 to 15 minutes). The Chief of Staff acts on what changed, or on nothing, writes the board, and runs the watch again. It never ends its turn while a Delegation runs, so it never depends on an idle wake. The cost is one tool call per cap with no tokens spent while the shell sleeps; the risk is any limit on turn or command length the editor applies (9).
- **A `stop` hook as the net.** With the human's yes (it is persistent configuration), a project `stop` hook that, while a run is open (a marker file in the run folder), returns `followup_message: "Heartbeat: check the orchestrate board"` with `loop_limit: null`. Whether it can wait between turns rather than fire at once is (8); fired at once it turns every turn end into another turn, which is the foreground watch with less control. So it is the net, not the heartbeat.

## 4. Recommended changes to the skill (prose only; nothing edited)

### 4.1 `await`, per harness

**HARNESSES.md, the `await` verb.** Redefine it as "wait for the next event, and never wait on one signal alone": every harness's `await` names a primary event and a heartbeat, and the Chief of Staff treats a wake as "something may have changed", never as "a report is final". DESIGN.md's "Four verbs, three tiers" gains a sentence on why: a harness's turn-end signal comes once per turn, before the report can be final, and not at all for a stalled prompt or an external wait.

**claude-code-desktop.md.** Replace "Never poll" with:

- `await`: end the turn, with three things armed. (1) The app's continuation, which comes when the started sessions have ended their turns. (2) A `notify_when_idle` subscription (`SendMessage`, `to` the `local_…` id, no message) on each running Delegation, armed at `spawn` and re-armed on every wake that finds that Delegation not final. (3) The heartbeat (4.2). On each wake, check every Delegation's files, not only the one quoted. External waits (CI, the review workflow) are a background Bash command that exits on the change or after a cap; a wake from one that found nothing starts the next one, or leaves it to the heartbeat.
- `message`: before the first message, check that the Chief of Staff and each Delegation are in the same permission-mode class (both bypassing, or both not), or that `crossSessionInbound` is `accept`; otherwise messages are held and dropped after five minutes. The Dispatch Plan says which.
- Limits: the continuation waits for every working sibling; a Delegation stopped on a permission prompt wakes nobody; nothing local runs while the machine sleeps, so an unattended run needs **Keep computer awake** on, which the human sets.

**cursor.md.** Replace "end the turn … Never poll" with: `await` is a foreground watch, as 3.3 describes, re-run after each event or cap; the Chief of Staff does not end its turn while a Delegation runs. The background subagent's completion notice, where it comes, is one more event the watch sees. A `stop` hook heartbeat is offered in the Dispatch Plan as a persistent change, on the human's yes.

### 4.2 The heartbeat

Add to SKILL.md step 6 a heartbeat that every run on a harness with a scheduler arms at the first `spawn` and removes at close-out or when the run parks:

- **Claude Code desktop and CLI:** one recurring `CronCreate` task, every 10 minutes (`*/10 * * * *`, which jitter starts 0 to 5 minutes late). Ten minutes is inside the review workflow's "minutes apart" pace from step 7, keeps an unattended hour to about six short turns, and a recurring task re-arms itself with no help from the turns between. `*/5` is the cheaper choice per fire, since it lands inside the prompt cache, for a run with Delegations that report in minutes. The prompt is plain text that says what each fire does (as in 2.3), and that a fire with nothing new logs one line and ends at once. Recreate it before seven days pass; recreate it after `--resume`, which drops background commands and monitors and keeps unexpired crons.
- **Cursor:** the foreground watch's cap is the heartbeat (10 to 15 minutes).
- **Tier 3:** none; the human is the event.
- The board records the heartbeat's id, so `--status` shows it and `--resume` re-arms it.

### 4.3 The Brief Contract: a report is final before the turn ends

Add to BRIEF.md item 8 (and the QA brief's item 8): "Never end a turn with work still running that the report depends on. Wait for a background command to finish in the same turn, or, if the turn must end, write the report with `**Final:** no, waiting on <what>` and end the turn; write it again with `**Final:** yes` when that work finishes." Add a `**Final:**` line to both report forms, so the Chief of Staff can tell an early wake from a report at a glance, and step 7 then verifies only a report that says `yes`. A report that says `no` is not sent back; the Chief of Staff re-arms its wait on that Delegation.
