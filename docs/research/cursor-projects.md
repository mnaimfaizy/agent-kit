# Cursor Projects and the `orchestrate` skill

Research for the `orchestrate` skill ([HARNESSES.md](../../.claude/skills/orchestrate/HARNESSES.md)): what Cursor Projects is, how its coordinator delegates, and whether `orchestrate` should use it as an Executor, as its Chief of Staff, or not at all. Cloud Agents themselves are covered in [cursor-orchestration.md](cursor-orchestration.md) and not repeated here.

## 1. What Projects is

**The idea.** A Project "lets you take on larger bodies of work, such as a feature, a migration, or a full app" ([changelog](https://cursor.com/changelog/projects), 2026-09-10). You direct it by chatting with its **coordinator agent**, which plans, delegates to agents that write the code, and brings the work back for you to check. The coordinator "doesn't write code itself" ([Projects docs](https://cursor.com/docs/agent/projects)). It runs "as many in parallel as the work needs" (changelog, 2026-09-10); the blog says "thousands of subagents" ([blog](https://cursor.com/blog/projects), 2026-09-10). Projects "run on Cloud Agents" and appear in the left-hand nav of the Agents Window (docs).

**Status.** Beta, "rolling out to all users" from 2026-09-10 (changelog). Multiplayer added in beta from 2026-11-10 ([blog](https://cursor.com/blog/projects-multiplayer)). Every Projects API endpoint "is in beta and may change" ([API](https://cursor.com/docs/cloud-agent/api/endpoints.md#projects), read 2026-11-14).

**Creating one.**

- **UI** (docs): **New Project** in the sidebar's Projects section; pick an icon and name (empty name means "New Project"); choose a **workspace repository** and the **coordinator's model**; **Create Project**; describe what to build. Existing top-level Cloud Agent chats can be dragged in or added with **Add to Project**; a local chat is "converted to Remote Control" before it is added.
- **API:** `POST /v1/projects` (section 7).
- **CLI:** none. Colin (staff, 2026-09-16, [forum](https://forum.cursor.com/t/cursor-projects-for-cli-and-also-self-hosted-cloud-agents/171697)): "The CLI can't create or drive a Project at the moment"; Projects are made and managed in the desktop app's Agents Window. iOS can message the coordinator but has no Projects view (workers show as separate agents); web and mobile Projects views are "in progress" (same post).
- **A remote repository is needed.** The UI asks for a workspace repository (docs). A community request (BryanZ, 2026-10-30, [forum](https://forum.cursor.com/t/projects-coordinator-that-dispatches-to-local-agents-by-default-not-cloud-agents/171423)) reports having to push to an origin first; no doc states the rule: **UNCONFIRMED**.

**What it holds.**

- **The coordinator chat.** One coordinator per Project per person, by design; it uses the selected model's normal context window and auto-summarizes older turns; `/summarize` or `/compact` compress it manually (Dean Rie, 2026-09-17, [forum](https://forum.cursor.com/t/projects-context-usage/171803)).
- **Shared context.** "A set of files that sync across every cloud and local machine its agents use"; agents store research, artifacts, codebase knowledge and your preferences there for later agents (docs; changelog 2026-09-10). Dean Rie calls this the **Context** tab, where long-lived notes survive summarization (2026-09-17). In multiplayer, the Project store mounts at `/cursor/stores/self` and each person's personal store, which holds "your preferences and skills", at `/cursor/stores/user`, unseen by teammates (docs).
- **A task board.** "Everyone works from the same tasks in the Project's list and board" (docs, multiplayer section). The multiplayer blog lists "Plans, Docs, Designs, Tasks, Skills, Memories" as shared elements, and the board shows "the PR behind each task" (2026-11-10).
- **Subscriptions** (section 4) and an **Agents list** of the agents the coordinator started (docs; API section 7).
- **Not issues.** Nothing says a Project holds or syncs GitHub issues; the on-call example mentions Linear boards to watch (multiplayer blog). Issue-tracker integration as a Project feature: **UNCONFIRMED**.

**Plan, cost and version requirements** (docs, read 2026-11-14):

- Every plan with Cloud Agents: Premium and higher, Teams, Enterprise, legacy paid. Not Free, Plus, legacy Hobby, or Privacy Mode (Legacy).
- Enterprise teams need Cursor 3.21.9 or later; sharing a Project needs a team account and 3.26.13 or later.
- Billing: each agent bills its own work at its model's rate. Mohit (staff, 2026-09-22, [forum](https://forum.cursor.com/t/issue-in-new-feature-called-projects/172589)): "This is how Projects works today": the coordinator starts several parallel agents that "each bill their own work"; a broad opening prompt made parallel agents each re-read the repository (the reporter cites close to 500 million tokens for a basic task, a community figure). There is **no built-in spend cap**; one is "a fair ask, and we're tracking feedback like this". His advice: a rule to use one agent per task, one narrow task at a time, and stopping unexpected agents from the Agents list.
- In multiplayer, each member's chat "runs and bills as them" (docs).

**Beta limits found.** No CLI; no local-only coordinator (section 3); no spend cap; local MCP servers do not reach the coordinator (section 6); local-agent folder mapping bug (section 3); stable IDs for user and coordinator messages absent (community report, Lutz_Leonhardt, 2026-09-26, [forum](https://forum.cursor.com/t/i-tested-the-projects-beta-for-three-days-what-worked-and-where-decisions-got-lost/172974)). No documented cap on agents per Project; the API lists only a Project's newest 1,000 agents (section 7).

## 2. How it delegates

**Cloud by default, local when asked or needed.** "A Project runs on its own cloud machine, so closing your laptop doesn't stop it. When something needs testing on your machine, the coordinator starts a local agent" (docs). Colin (2026-09-14, [forum](https://forum.cursor.com/t/projects-coordinator-that-dispatches-to-local-agents-by-default-not-cloud-agents/171423/5)): "Projects is deliberately cloud-first for now", and "There isn't a local-only coordinator mode today." Colin (2026-10-22, [forum](https://forum.cursor.com/t/agents-window-projects-cant-use-my-local-mcp-servers-cursor-mcp-json-even-in-cloud-local/175734)): "the Project's coordinator always runs as a Cloud Agent on Cursor's servers"; to get a local worker, make sure "Run on includes your machine, not just Cloud", then "ask for a local agent by name" in the Project chat.

| Coordinator model | Yes, at creation (docs).                                                                                                                                           | `model` on `POST /v1/projects` (API).                                                                                                  |
| Worker model      | Only by asking the coordinator in chat, or by a Project rule (Mohit suggested rules to shape worker behaviour, 2026-09-22). A per-worker setting: **UNCONFIRMED**. | No field. Only through the coordinator's prompt: **UNCONFIRMED** whether it is honoured.                                               |
| Repository        | The workspace repository, at creation (docs).                                                                                                                      | `repos` on create, same shape as Create An Agent (API).                                                                                |
| Worker branch     | Not documented. Whether a Project's cloud worker uses Cloud Agents' default `cursor/...` branch: **UNCONFIRMED**.                                                  | No field on create; no Projects endpoint starts a worker.                                                                              |
| Worker brief      | Written by the coordinator. The human can only shape it through the coordinator chat.                                                                              | Same: only the coordinator's prompt and follow-ups.                                                                                    |
| Cloud or local    | "Run on" in the app; ask for a local agent by name (Colin, 2026-10-22).                                                                                            | `env` on create (cloud, pool or machine, as for Create An Agent): whether that places the coordinator or the workers: **UNCONFIRMED**. |

**Parallelism.** Yes, as many agents in parallel "as the work needs" (changelog); the blog's feature flow is "research, record findings, write a plan, then send agents to implement and test parts in parallel" (2026-09-10, paraphrased).

**Isolation.**

- **Cloud workers** are Cloud Agents (docs: Projects "run on Cloud Agents"; Lutz_Leonhardt's community report counts 20 agents and 5 PRs). A Cloud Agent gets its own VM with the repository cloned ([cursor-orchestration.md](cursor-orchestration.md), and [SDK](https://cursor.com/docs/sdk/typescript)). That every Project worker gets its own VM and branch, rather than sharing one: **UNCONFIRMED** (likely, not stated for Projects).
- **Local workers have no isolation.** Kevin Neilson (staff, 2026-10-19, [forum](https://forum.cursor.com/t/project-coordinator-with-local-agents/175337)): the local agent "works in that machine's existing checkout and branch"; "one worker can run multiple agents at once", and "Nothing coordinates file edits between them, so two agents could end up editing the same files at the same time." His advice: one checkout per parallel agent (a separate `git worktree` with its own worker, each CLI worker with its own `--data-dir`), or ask the coordinator to run local work one agent at a time.

## 3. "Starts a local agent"

**It is a Self-Hosted Machine worker**, the My Machines kind (Kevin Neilson, 2026-10-19). Two ways to have one:

- **Desktop app, no CLI:** Settings → Agents → Self-Hosted Workers → **Enable local self-hosted workers** (on some versions called **Remote Control**). Cursor starts one worker per local repository folder open in the Agents Window, **so the Project's repository must be open there** (Kevin Neilson, 2026-10-19).
- **CLI:** `agent login`, then `agent worker start` in the repository checkout, kept running ([My Machines](https://cursor.com/docs/cloud-agent/self-hosted/my-machines)); `--worker-dir` names the checkout(s), `--name` the machine, `--computer-use` enables clicking, typing and screenshots. Suited to a devbox where the app is not open (Kevin Neilson).
- **Either way:** self-hosted machines must be allowed for the team in the cursor.com dashboard's Cloud Agents section ("Enable Self-hosted Machines" or "Enable Remote Control for Team"); the first time the coordinator runs something on a machine **it asks you to approve it**; the machine must stay awake with Cursor or the CLI worker running (Kevin Neilson, 2026-10-19). My Machines needs a personal credential, not a service-account key (docs).
- **Shipped:** Self-hosted machines, 2026-09-02; Remote control for local agents (iOS), 2026-10-06 ([changelog p.2](https://cursor.com/changelog/page/2)). Colin called the local path "still early" on 2026-09-14.

**What it can reach** ([My Machines](https://cursor.com/docs/cloud-agent/self-hosted/my-machines), read 2026-11-14): the agent loop runs in Cursor's cloud, but "terminal commands, file edits, browser actions, and other tool calls execute on your machine", in the `--worker-dir` checkout, with the machine's own tools, credentials and network (dashboard secrets are not passed). So it can reach the local stack and a browser. Stdio MCP servers run on the machine; HTTP/SSE MCP servers run on Cursor's backend. Colin (2026-10-22): the local worker "should load the command (stdio) servers from your `~/.cursor/mcp.json`"; the coordinator "can't see those tools itself".

**Which folder.** Mohit (staff, 2026-09-21, [forum](https://forum.cursor.com/t/cursor-project-local-agent-initially-accessed-a-different-local-repository-than-the-project-repository/172432)): a Project's local run "uses a machine you already have connected and runs in the folder that Cursor window has open", not a clone of the Project repository; for a Project that names a repository this "isn't intended". The repository-match guard that protects chat-triggered `worker=` runs "just didn't apply" to the coordinator's dispatch. Workaround: open only the Project's repository in Cursor windows. No fix announced as of the thread's last post (2026-09-22).

**A run folder outside the repository.** Nothing documents a Project's local agent writing outside its worker directory. Writes to `delegations/<id>/report.md` in the Chief of Staff's gitignored run folder: **UNCONFIRMED**, and unlikely to be safe given the folder-mapping bug.

**User-invoked skills such as `/qa-plan`.** A skill with `disable-model-invocation: true` "is included only when you explicitly invoke it with `/skill-name`" ([Skills](https://cursor.com/docs/skills)). A local worker's brief is written by the coordinator, not typed by the human; whether a coordinator-written `/qa-plan 12` counts as that explicit invocation, and whether the human can type into a Project's local worker at all: **UNCONFIRMED**. Self-hosted workers get project skills from the repository only (section 6), so `qa-plan` and `manual-qa` must be in the repository for a worker to see them.

**Reported failures.** A community tester on Linux reports the coordinator's local dispatch "did nothing" and everything ran in the cloud (Lutz_Leonhardt, 2026-09-25, community).

## 4. Events

**Subscriptions on a Project** (docs): ask the coordinator to watch a Slack channel, follow your pull requests, or run on a schedule; a **Listening** pill appears above the chat input, and each subscription is removed from the Listening list. Example events: "PR activity in a repository, CI runs on a branch", a channel message, a daily 8:00 AM schedule. The blog adds that it can "fix CI and act when PRs open or merge" (2026-09-10). If GitHub is not connected, the menu offers "Connect GitHub".

**Review comments after CI is green.** The Cloud Agents subscription model delivers, for one PR, "comments, reviews, and lifecycle changes", and CI results on a branch; events arrive as follow-up messages in the same conversation; a subscription lasts at most 180 days; "Subscriptions need an agent that a person owns" ([Capabilities](https://cursor.com/docs/cloud-agent/capabilities)). Nothing ties PR activity to CI state, so a review comment posted after CI turns green should arrive as PR activity. That a Project's "follow your pull requests" subscription uses this same per-PR mechanism, and so delivers late review comments to the coordinator: **UNCONFIRMED**. A community tester reports one review bot's 18 findings were all fixed and a second bot's comments were ignored, and that review-comment ownership between coordinator and workers was unclear (Lutz_Leonhardt, 2026-09-25, community).

**Worker completion to the coordinator.** "Every agent turn sent a completion event to the orchestrator" (Lutz_Leonhardt, 2026-09-25, community report; no doc states it): **UNCONFIRMED** as documented behaviour.

**What an API caller gets** ([API](https://cursor.com/docs/cloud-agent/api/endpoints.md), read 2026-11-14): no Projects-specific events. The coordinator is an agent: read its replies with **Stream An Agent**, `GET /v1/agents/{coordinatorAgentId}/stream` (SSE, beta, stays open across runs, resumable with `Last-Event-ID`; events `status`, `assistant`, `thinking`, `tool_call`, `interaction_update`, `heartbeat`, `error`, `done`; 50 open streams per caller). Or poll `GET /v1/projects/{id}/agents` and each agent's runs. Webhooks are "coming soon" in v1; the legacy v0 API has them, but whether v0 webhooks fire for a Project's coordinator or workers: **UNCONFIRMED**.

**Telling a local session.** Nothing pushes to a local Claude Code or Cursor session. A local Chief of Staff would have to hold an SSE stream open or poll. No doc says a Project can notify a local session.

## 5. Control

- **Follow-up to the Project:** `POST /v1/agents/{coordinatorAgentId}/runs`. It returns `409 agent_busy` while the coordinator works; use `delivery: "steer"` instead, which answers `202` with `steered` or `queued`, and may be `403 feature_unavailable` on some accounts. Retrying a steer after an error can deliver it twice (API, read 2026-11-14).
- **Follow-up to one worker:** `GET /v1/projects/{id}/agents` returns each worker with Get An Agent fields, so it has an agent id; that `POST /v1/agents/{workerId}/runs` is allowed on a coordinator-started worker, and what the coordinator then sees of it: **UNCONFIRMED**. In the UI, Voice Chat can "switch between workers in a Project that has them" ([changelog](https://cursor.com/changelog), 2026-11-06), and iOS shows workers as separate agents (Colin, 2026-09-16).
- **Stop:** `POST /v1/agents/{id}/runs/{runId}/cancel`; terminal, a new run is needed to continue (API). In the UI, stop unexpected agents from the Agents list (Mohit, 2026-09-22). Archiving a Project (`POST /v1/projects/{id}/archive`) leaves it readable; whether it stops running workers: **UNCONFIRMED**.
- **Approve or refuse actions:** the only documented approval is the first local run on a machine (Kevin Neilson, 2026-10-19) and, in multiplayer, the coordinator "asks before sharing that person's personal files or connector data" (docs). No tool-call approval API exists: `tool_call` events report only running and completed (API).
- **Questions to the human:** in the coordinator chat. A community tester reports the coordinator listed defaults and asked him to confirm, then started the agent when he answered a different question, and that "defaults were treated as approved" (Lutz_Leonhardt, 2026-09-25/26, community). In multiplayer, a side chat from another person's coordinator "can't ask you questions" (docs). Whether a worker can ask the human directly, or only through the coordinator: **UNCONFIRMED**. How an API caller tells a question from a status line in the stream (perhaps `interaction_update`): **UNCONFIRMED**.

## 6. Skills, rules and context

- **Repository skills.** Cursor loads `.agents/skills/` and `.cursor/skills/` (project), `~/.agents/skills/` and `~/.cursor/skills/` (user), and for compatibility `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/`, `~/.codex/skills/` ([Skills](https://cursor.com/docs/skills)). Cloud Agents work in a clone, so project skills in the repository come with it. That a Project's coordinator and its workers load repository skills as any Cloud Agent does: **UNCONFIRMED** (no Projects page says so).
- **User skills.** Only `~/.cursor/skills/` syncs to Cloud Agents, and only with **Sync Skills for Cloud Agents** on; synced skills load "only in Cloud Agents you start yourself" (Skills). `~/.agents/skills/`, `~/.claude/skills/` and unsynced skills are never copied to Cloud Agents, remote SSH sessions or self-hosted workers; on self-hosted workers, "use project skills from the repo or bake skills into the worker image" (Skills). Whether a coordinator-started worker counts as one "you start yourself": **UNCONFIRMED**. The Project personal store holds "your preferences and skills" (docs), a separate mechanism whose relation to synced skills is **UNCONFIRMED**.
- **Rules and AGENTS.md.** Neither the Projects page nor the Cloud Agents page says how rules or AGENTS.md load for a Project. Staff advise adding rules to steer it (Mohit, 2026-09-22), so rules are read in some form; which (repository `.cursor/rules`, AGENTS.md, a Project-level rule): **UNCONFIRMED**. Cloud Agents and self-hosted workers do run command hooks from `.cursor/hooks.json` ([Cloud Agents](https://cursor.com/docs/cloud-agent); [My Machines](https://cursor.com/docs/cloud-agent/self-hosted/my-machines)).
- **MCP.** The coordinator loads MCP servers only from the Cloud Agents MCP settings at cursor.com/agents, never from `~/.cursor/mcp.json` (Colin, 2026-10-22).

## 7. API

Base `https://api.cursor.com`. **Auth:** Basic (the key as username, empty password) or Bearer. Projects need a **user API key**: a service-account key gets `403 user_required` on create and lists no Projects. Owner-only actions return `403 owner_required` to others. A team admin can turn Projects off: `403 projects_disabled` on create, `404 project_not_found` for the team's Projects. Every Projects endpoint may also return `403 feature_unavailable`, `403 plan_required`, `429 rate_limit_exceeded`, `500 internal_error`. Errors are `{ "error": { "code", "message" } }`. All from the [API reference](https://cursor.com/docs/cloud-agent/api/endpoints.md#projects), read 2026-11-14. The TypeScript SDK has no Projects methods (read 2026-11-14).

## Three options

Each mapped onto the four verbs ([HARNESSES.md](../../.claude/skills/orchestrate/HARNESSES.md)).

### (A) Projects as an Executor for building Delegations; the local Chief of Staff verifies

One Project per building Delegation (or one Project fed one Delegation at a time), started from the Chief of Staff's shell.

| Verb      | How                                                                                                                                                                                                                                                                  |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spawn`   | `POST /v1/projects` with the brief as `prompt.text`, `repos`, and the plan's model as `model`, which sets the **coordinator's** model only. Handle: `project.id` plus `coordinatorAgentId`. The worker's model, branch and exact brief are the coordinator's choice. |
| `message` | `POST /v1/agents/{coordinatorAgentId}/runs`, with `delivery: "steer"` while busy. Reaches the coordinator, which may or may not pass it on.                                                                                                                          |
| `await`   | Hold `GET /v1/agents/{coordinatorAgentId}/stream` open, or poll `/v1/projects/{id}/agents` and runs. No push to the local session; no v1 webhooks.                                                                                                                   |
| `report`  | Cannot reach the run folder. The coordinator's last message carries the report; the Chief of Staff writes it into `report.md` (as HARNESSES.md allows).                                                                                                              |

**For:** survives the laptop closing; the Project follows its own PRs and CI and can fix them; the human can open and steer it from desktop or phone, close to a Live Session.

**Against:** a coordinator inside an Executor doubles the planning layer and the cost (parallel agents each re-reading the repo, no spend cap); the brief the Chief of Staff wrote is rewritten by another planner before any worker sees it, so the Brief Contract's scope fence and stop points are only as good as the coordinator's obedience; the Dispatch Plan's model is not the worker's model; needs a user API key the skill must never type; beta API. It is a strictly heavier form of the Cloud Agent opt-in already in HARNESSES.md, which gives `spawn` the model, branch and brief directly.

### (B) Projects as the Chief of Staff, fed orchestrate's rules

The human runs a Project and gives its coordinator `orchestrate`'s rules (in the repository's skills or rules, or pasted in).

| Verb      | How                                                                                                                      |
| --------- | ------------------------------------------------------------------------------------------------------------------------ |
| `spawn`   | The coordinator's own delegation. No parameter fixes the worker's model, branch or working copy; the human asks in chat. |
| `message` | The coordinator talks to its own workers (mechanism not documented).                                                     |
| `await`   | Native: workers report to the coordinator (community-reported completion events), and PR/CI/Slack subscriptions wake it. |
| `report`  | The shared context store (`/cursor/stores/self`), not a run folder in the human's checkout.                              |

**For:** everything the skill builds by hand (board, parallel Executors, waking on PR events, a phone-readable chat) is native; no local session has to stay open.

**Against:** the coordinator would verify its own workers' reports inside the system that ran them, so the verification step is no longer independent of the work; it cannot run `regate` in a detached worktree of the branch on the human's machine, nor `git merge-tree` against the human's checkout; it cannot take a user-invoked skill, so QA would be a coordinator-written worker brief; local workers share one checkout and can land in the wrong folder; community reports of decisions lost and defaults treated as approved are the Decision Request failure the skill exists to prevent; the skill's own user-level copy would not load (only `~/.cursor/skills` syncs, and only for agents you start yourself). It would also be a new harness id with no tool signature, at Support Level `documented`.

### (C) Don't use it

Keep the Cursor harness file as it is: local background sub-agents in worktrees for building and analysis, a headless `agent -p` run for QA, and a single Cloud Agent per building Delegation only when the human asks, to answer its own PR's review.

**For:** every verb stays under the Chief of Staff's control with documented parameters; no beta dependency; no extra spend. **Against:** no Project-level PR babysitting or phone view of the whole run; the human gets those per Delegation only through the Cloud Agent opt-in.

## Recommendation

**(C) now, and (A) never as a default.** Projects is a second Chief of Staff, not an Executor: its whole value is the planning and delegation layer that `orchestrate` already supplies and must keep. Where the human wants cloud work that survives the laptop and follows its own PR, a single Cloud Agent (already the opt-in in HARNESSES.md) gives the same benefit with `spawn` choosing the model, branch and brief directly. Revisit when Projects documents per-worker model and branch, an API to start a worker, webhooks, and a repository-scoped local dispatch.

## UNCONFIRMED

1. Whether the human or an API caller can set a Project worker's model, branch, or exact brief, other than by asking the coordinator.
2. Whether each cloud worker gets its own VM and branch, and what its branch is named.
3. Whether a Project's "follow your pull requests" subscription delivers review comments posted after CI is green to the coordinator, and to which agent.
4. Whether a coordinator-written or human-typed `/qa-plan <n>` runs a `disable-model-invocation` skill in a Project worker, and whether the human can type into a local worker.
5. Whether a Project's coordinator and workers load repository skills, `.cursor/rules` and AGENTS.md, and which rules apply.
6. Whether a coordinator-started worker counts as an agent "you start yourself" for synced user skills, and how the personal store's skills relate to them.
7. Whether `POST /v1/agents/{workerId}/runs` works on a coordinator-started worker, and whether archiving a Project stops its workers.
8. Whether v0 webhooks fire for a Project's coordinator or workers; v1 has none.
9. What `env` on `POST /v1/projects` places: the coordinator, its workers, or both.
10. Whether a Project's local agent can write outside its worker directory (to a run folder).
11. Worker completion events to the coordinator (community-reported, not documented), and whether a worker can ask the human a question directly.
12. Whether Projects requires the repository to have a remote origin.
13. Any Projects API beyond the seven endpoints (tasks, shared context, subscriptions, members, starting a worker).
14. Whether the local-agent folder-mapping bug (Mohit, 2026-09-21) has been fixed.
15. Whether a Project holds or syncs GitHub issues.
