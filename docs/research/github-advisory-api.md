# What the GitHub advisory API lets a Security Response Run read and do

Research for wayfinder ticket [#324](https://github.com/mnaimfaizy/agent-kit/issues/324), part of map [#323](https://github.com/mnaimfaizy/agent-kit/issues/323) (Security Response Run). The question: what can a local session read and do about this repository's security advisories with `gh` and `gh api`, which token each operation needs, and which state a run can check for itself on resume versus what the human must report.

- **Read on:** 2026-11-19. Docs pages carry no publish date, so a fact from a docs page is dated by the read. REST API version `2022-11-28` (the `X-Github-Api-Version-Selected` header on a live call).
- **Sources:** primary only.
  - REST: [Repository security advisories](https://docs.github.com/en/rest/security-advisories/repository-advisories) (list, get, create, private report, update, request CVE, create temporary private fork), [Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens) ("Repository security advisories" section).
  - Product docs: [Collaborating in a temporary private fork](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/collaborating-in-a-temporary-private-fork-to-resolve-a-repository-security-vulnerability), [Publishing a repository security advisory](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/publishing-a-repository-security-advisory), [Editing a repository security advisory](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/editing-a-repository-security-advisory).
  - `gh`: the [manual's command index](https://cli.github.com/manual/gh) and the installed `gh 2.78.0` (`gh help`).
  - **Probed:** read-only `gh api` calls against this repository on 2026-11-19, listing only ids, states, dates, counts and field names. No advisory text was read into this note. Marked **probed**.
  - **Lived:** this repository's past responses (alpha.6 to alpha.10), as recorded in the maintainer's notes. Marked **lived**; these are observations, not documented guarantees.
- **UNCONFIRMED** marks anything no primary source states.

## Answer in one paragraph

Everything a run needs to _read_ is in one call: `GET /repos/{owner}/{repo}/security-advisories?state=draft` returns every draft with its state, severity, versions, credits (with acceptance state), collaborators, CVE id and `private_fork` (the fork's repository, or `null`). Fork PRs are then ordinary `GET /repos/{owner}/{fork}/pulls` calls. Every _write_ (PATCH body, severity, versions, credits, collaborators, `state=published`/`closed`, request CVE, create fork) is a single `gh api` call too, with a classic `repo` token or a fine-grained PAT with "Repository security advisories: write". `gh` has no native advisory command, so all of it goes through `gh api`. The one step the API cannot do is the advisory-level **Merge pull request(s)**: merging the private fork into upstream is a web-UI action only (UNCONFIRMED: no REST endpoint for it is documented), and here it also needs the human's admin ruleset bypass. So on resume a run can verify almost every state itself; the human reports only the advisory merge (and the run can still confirm it after the fact by checking that upstream `main` contains the fix commit), and any judgement (severity, triage outcome).

## Details and evidence

### Reading

- **States.** The list endpoint's `state` filter takes `triage`, `draft`, `published`, `closed`. CI-filed advisories arrive as `draft`; `triage` is for private vulnerability reports, whose `submission` field is non-null. **Probed:** this repo has 2 drafts, 6 published, 10 closed; both drafts have `submission: null`.
- **Fields.** **Probed:** a draft's keys are `author, closed_at, collaborating_teams, collaborating_users, comments, created_at, credits, credits_detailed, cve_id, cvss, cvss_severities, cwe_ids, cwes, description, ghsa_id, html_url, identifiers, private_fork, published_at, publisher, severity, state, submission, summary, updated_at, url, vulnerabilities, withdrawn_at`. Each `vulnerabilities[]` item has `package, patched_versions, vulnerable_functions, vulnerable_version_range`.
- **Selecting fields without leaking.** `gh api ... --jq` filters on the client, so a run can keep `description`/`summary` out of every log and file by projecting only metadata fields. The full body still crosses the wire to the local machine, which is fine under the map's "nothing leaves the machine" rule.
- **Who can read.** Unpublished advisories: admin or security manager, or a collaborator on that advisory. The REST page's scope line is "`repo` or `repository_advisories:read`".

### The temporary private fork

- **Name:** `{repo}-ghsa-xxxx-xxxx-xxxx` (repo name truncated to 80 chars, lower-case GHSA suffix), so a run can derive it, but `private_fork.full_name` on the advisory is authoritative.
- **CI:** "integrations, including CI, cannot access temporary private forks" and "status checks do not run on pull requests in temporary private forks". A run cannot get CI signal from the fork; local lint and tests are the only pre-merge check.
- **Merge rules:** individual PRs cannot be merged; merging is advisory-level, via **Merge pull request(s)**, which merges every open fork PR at once. Every open PR must be mergeable with no conflicts, and **only one PR may target `main`** (more blocks the merge). **Lived:** a second PR works after fast-forwarding the fork's `main` to upstream.
- **Rules bypass:** the docs say GitHub "won't enforce any of the protection rules" for the target branch on this merge. **Lived, contradicting that:** in this repo the merger needed the "main branch" ruleset's admin bypass. Rulesets may behave differently from classic branch protection here (UNCONFIRMED).
- **On publish:** "Publishing ... deletes the temporary private fork." **Probed:** all 6 published advisories have `private_fork: null`. The docs do not say what closing does to the fork (UNCONFIRMED).

### Writing

- **PATCH** takes `summary, description, cve_id, vulnerabilities, cwe_ids, credits, severity` **or** `cvss_vector_string` (never both), `state` (`published`, `closed`, `draft`), `collaborating_users`, `collaborating_teams`. Credits and arrays are whole-value replacements.
- **Publish:** "you should add a fix version ... prior to publishing", otherwise Dependabot alerts users with no safe version. The docs do not list what a `422` on publish requires (UNCONFIRMED).
- **Edit after publish:** the editing page says metadata and description can be edited and does not limit that to drafts. **Lived:** this repo PATCHes the public body before publishing, not after.
- **CVE:** public repos only; `202 Accepted`. Whether a CVE can be requested after publishing is not stated (UNCONFIRMED). This repo has requested none (**probed:** every `cve_id` is `null`).

### Tokens

- **Classic / `gh auth`:** the `repo` scope covers everything. **Probed:** the local `gh` token is an OAuth token with `repo`, and it lists drafts.
- **Fine-grained PAT:** "Repository security advisories" read for list/get/comments-read and fork creation (with an extra-permission mark), write for create, report, PATCH, comments-write and CVE. The org-level list needs write.
- **GitHub App / job token:** the fine-grained page lists these endpoints under PAT only, and this repo's CI already uses a separate `AGENT_KIT_ADVISORIES_TOKEN` secret because the job token cannot create advisories. A run should use the human's own `gh` login.
- **Rate limits:** ordinary core REST limits (5000/h for a user token; **probed** `X-Ratelimit-Resource: core`). One list call per resume is enough; the advisory endpoints have no special limit documented. `422` can also mean "the endpoint has been spammed".

### `gh`

There is no `gh advisory` or GHSA command in the installed `gh 2.78.0` or in the current manual's command index; everything above is `gh api`. Fork PRs are the exception: ordinary `gh pr` commands work with `--repo {fork}`. **Lived:** an extra git remote for the fork breaks `gh`'s default-repo detection; clone the fork into its own directory or always pass `--repo`.

## Automate vs human, on resume

- **A run can check for itself:** which drafts exist (new, gone, published, closed); severity, CWEs, versions, CVE id, collaborators, credits and their acceptance; whether a fork exists and the state of its PRs; whether upstream `main` and a release tag contain a fix SHA; publication.
- **The human must report:** that they clicked the advisory-level merge (the API has no merge action; the run can verify it afterwards from `main`); triage judgements; anything done only in a fork that has since been deleted by publishing (fork PR history is gone, so record fork PR numbers and fix SHAs on the board before publish).
- **A run must record itself, because the API won't show it later:** that a CVE was requested (until `cve_id` arrives), and the fork's PRs and SHAs (the fork disappears on publish).

## UNCONFIRMED

- No REST endpoint for the advisory-level "Merge pull request(s)" is documented.
- Whether advisory merges bypass repository rulesets (docs say protection is not enforced; lived experience here needed a bypass).
- What closing an advisory does to its fork.
- What a `422` on publish requires.
- Whether a CVE can be requested after publish.
- How merged fork PRs show (merged vs closed) after the advisory merge.
