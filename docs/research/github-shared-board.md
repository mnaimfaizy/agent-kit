# What GitHub can hold a Team Run's Shared Board in

Research for wayfinder ticket [#303](https://github.com/mnaimfaizy/agent-kit/issues/303) on map [#302](https://github.com/mnaimfaizy/agent-kit/issues/302): the opt-in **Team Run** mode of the `orchestrate` skill, where several teammates each run their own Chief of Staff over the spec tickets assigned to them, and all of them read and write one **Shared Board** on the tracker. A row of that board holds what a row of a run's local board holds today ([RUN.md](../../.claude/skills/orchestrate/RUN.md#board)): the ticket, its assignee, its Delegation state, its branch, its pull request and its open Decision Requests.

This note compares the surfaces only. It recommends nothing final: the choice is grilling ticket [#305](https://github.com/mnaimfaizy/agent-kit/issues/305).

## 1. Facts that hold for every surface

**Rate limits.** Every teammate's Chief of Staff calls GitHub with that teammate's own token, so each has their own budget.

- Primary: 5,000 REST requests per hour per user, and separately 5,000 GraphQL points per hour per user ([REST](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [GraphQL](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). A GraphQL call costs at least 1 point; a call that asks for at most 100 nodes per connection costs about 1.
- Secondary, shared by REST, GraphQL and the web UI: at most 100 concurrent requests; 900 points a minute on REST and 2,000 on GraphQL, where a GraphQL request with a mutation counts 5 and one without counts 1; and **no more than 80 content-generating requests a minute and 500 an hour**, a limit that "include[s] actions taken on the GitHub web interface" (same pages).
- Conditional reads are free: an authenticated request with `If-None-Match` that gets `304` "does not count against your primary rate limit" ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). This holds for REST only; GraphQL has no ETag.
- The same page asks for writes to be made "serially instead of concurrently" and to "wait at least one second between each request".

A heartbeat every 3 minutes is 20 beats an hour. Reading the board on each beat, and writing only the rows that changed, stays far inside every primary limit on every surface below. The only limit a Team Run can come near is the 500 content-generating requests an hour, and only on a surface that writes many objects per beat. Whether an *edit* (of an issue body, a comment, a label, a project field) counts as content-generating is **UNCONFIRMED**: the docs name content creation without listing which calls count.

**No optimistic locking anywhere.** No write the board would use takes a precondition:

- REST: "Conditional requests for unsafe methods" are "not supported unless otherwise noted" for an endpoint ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). "Update an issue" documents no `If-Match` or version parameter ([issues](https://docs.github.com/en/rest/issues/issues#update-an-issue)); neither does "Update an issue comment" ([comments](https://docs.github.com/en/rest/issues/comments)).
- GraphQL (**schema**): `UpdateIssueInput` takes `id, title, body, assigneeIds, assignees, milestoneId, labelIds, labels, state, stateInput, statusId, projectIds, issueTypeId, issueType, issueFieldUpdates, agentAssignment` plus `clientMutationId`; `UpdateIssueCommentInput` takes `id, body`; `UpdateProjectV2ItemFieldValueInput` takes `projectId, itemId, fieldId, value`. None carries an expected version or timestamp.

So any value two writers both rewrite is **last write wins**, with no error to the loser. A writer can read `updated_at` (REST) or `updatedAt` (GraphQL) just before writing and back off when it moved, but the gap between that read and the write is still a race. What differs between the surfaces is **how much one write replaces**: the whole board, one row, or one cell. And because a Team Run partitions tickets by assignee, a surface where each ticket's row is a separate object written only by its assignee's Chief of Staff has no two writers on one value at all, except around a reassignment (a "Not yet specified" item on the map).

**Public repositories.** Issues, comments, labels, sub-issue links and assignees on a public repository are readable by anyone, so whatever a row holds there (branch names, pull request links, Decision Request headings) is public. Projects and issue fields are the two exceptions, below.

## 2. The surfaces

### A. The spec issue's body

The whole board as a Markdown table in the spec issue's body (or in a fenced section of it, below the spec text).

- **gh:** `gh issue edit <n> --body-file -` writes the body; `gh issue view <n> --json body,updatedAt` reads it (**gh help**). Both are long-standing; version **UNCONFIRMED**, but present in 2.102.0.
- **Permissions:** "Issue owners and users with push access or Triage role can edit an issue" ([REST issues](https://docs.github.com/en/rest/issues/issues#update-an-issue)). The organization roles table puts "Edit others' issue titles and bodies" at Moderate, Write, Maintain and Admin, not Triage ([roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)): the two pages disagree on Triage, so a teammate with Triage only is **UNCONFIRMED**. Write is enough in either reading. On a personal-account repository (this one is owned by a user), collaborators are the only role besides the owner; their page lists issue creation, assignment, labels and comments but does not name editing another person's issue body ([personal repository](https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository)): **UNCONFIRMED**, though collaborators have push access, which the REST page names.
- **Concurrency:** the body is one value. Every write replaces the whole board, so two Chiefs of Staff writing within the same read-write window lose one side's rows. This is the same hazard `RUN.md` names for `--status` ("a second writer to the board would lose one side's change"), now across machines. It also races the human editing the spec text in the web UI, if the board shares the body with the spec.
- **Rate limits:** 1 read (free with a `304` on REST) and 1 write per beat that changed something. Negligible.
- **Size:** the body's length limit is not in the REST docs. The API error `Body is too long (maximum is 65536 characters)` is widely reported but not documented: **UNCONFIRMED**. A row is about 200 characters, so the limit is not near for a spec of tens of tickets.
- **UI:** renders as a table at the top of the issue, where everyone opening the spec sees it. Edits show an "edited" marker and an edit history; they post no timeline event and, per common experience, notify no one (**UNCONFIRMED**).
- **Public repos:** public.

### B. One edited, pinned comment on the spec issue

The whole board in one comment, pinned to the top of the spec issue.

- **gh:** `gh issue comment <n> --edit-last [--create-if-none]` edits *the current user's last comment* (**gh help**), which is the wrong comment as soon as that user, or their Chief of Staff, comments on the spec again; so a board comment would be written by its id, with `gh api -X PATCH repos/{o}/{r}/issues/comments/{id}`. Pinning has no `gh` command in 2.102.0 (`gh issue pin` pins an issue, not a comment); it is `gh api -X PUT repos/{o}/{r}/issues/comments/{id}/pin` and `DELETE` on the same path to unpin ([comments](https://docs.github.com/en/rest/issues/comments)), or the GraphQL mutations `pinIssueComment` / `unpinIssueComment` (**schema**; `IssueComment` also has `isPinned`, `pinnedBy`, `viewerCanPin`).
- **Permissions:** a comment is edited by its author, or by others at Moderate, Write, Maintain or Admin ([roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization): "Edit anyone's comments on issues"). One board comment is authored by one teammate, so every other teammate's Chief of Staff needs Write (or Moderate) to edit it. Who may pin a comment is not stated by the changelog or the REST page: **UNCONFIRMED** (a non-GitHub write-up says write access, and one pinned comment per issue; also **UNCONFIRMED**).
- **Concurrency:** identical to A: one value, whole-board rewrite, last write wins. It does not race the human's spec text, which is its one gain over A.
- **Variant, one comment per teammate:** each Chief of Staff keeps its own comment holding only its own tickets' rows. Each writer edits only what it authored, so no two writers share a value and any role that can comment suffices. The cost: the whole board is assembled by reading every board comment, and only one comment can be pinned (if the one-pin claim holds), so the rest sit in the timeline.
- **Rate limits:** as A.
- **UI:** shown at the top of the issue when pinned (changelog: "pin a comment to the top of an issue"). Without a pin, an early comment scrolls away under later discussion.
- **Public repos:** public.

### C. Per-ticket state on the sub-issues

Each spec ticket is already a sub-issue of the spec, so its row lives on the ticket itself and the board is assembled by reading the spec's sub-issues. The pieces:

- **Assignee:** already on the ticket and set by people, as the map requires. The Chief of Staff only reads it.
- **Delegation state as labels** (for example `team:running`, `team:parked`).
- **Branch, pull request, Decision Requests in one comment** per ticket, edited in place by the Chief of Staff of the ticket's assignee. A pull request that says `Closes #n` also shows on the ticket itself (`closedByPullRequestsReferences` in `gh issue view --json`).
- **Issue fields** (new in 2026) instead of labels or the comment: typed single-select, text, number and date fields, defined once per organization or user, up to 25 ([managing issue fields](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-fields-in-your-organization)). Public preview from 2026-03-12, GA from 2026-07-02 (changelog titles).

Detail:

- **gh:** `gh issue view <n> --json subIssues,subIssuesSummary,parent,assignees,labels,closedByPullRequestsReferences` reads it; `gh issue edit --add-label / --remove-label`, `--add-sub-issue`, `--parent`, and `gh issue create --parent` write it (**gh help**, 2.102.0; the version that added the sub-issue flags is **UNCONFIRMED**). The per-ticket comment is written by id with `gh api`, as in B. Issue fields have no `gh` flag and no `gh issue view --json` field in 2.102.0 (**gh help**); they are written with the GraphQL mutation `setIssueFieldValue` (input `issueId, issueFields`) or `updateIssue`'s `issueFieldUpdates` (**schema**), with `gh api graphql`.
- **Permissions:** labels and assignment need Triage or above ([roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)); without push access the REST update endpoint drops label changes "silently" ([REST issues](https://docs.github.com/en/rest/issues/issues#update-an-issue)), so a teammate with too little access sees no error. A teammate's own comment needs only the right to comment. The repository's labels must exist first, created once by someone with Write. Who may set an issue field value is not stated: **UNCONFIRMED**. Who may add a sub-issue is not stated either ([sub-issues REST](https://docs.github.com/en/rest/issues/sub-issues)): **UNCONFIRMED**; the board only reads the links, which the spec already made.
- **Concurrency:** each ticket's row is its own object, written only by its assignee's Chief of Staff, so teammates never write the same value. Labels are additive per label: `POST .../labels` adds and `DELETE .../labels/{name}` removes one, while `PUT` replaces the whole set ([labels](https://docs.github.com/en/rest/issues/labels)); the add/remove calls do not clobber a label a human added meanwhile. Moving a state is two calls (remove the old label, add the new), so a reader between them can see zero or two state labels. An issue field holds one value, so a state change is one write.
- **Rate limits:** reading the board is one GraphQL query for the spec's sub-issues with their labels, assignees and comments (about 1 point for up to 100 sub-issues), or 1 + N REST calls. Writing is per changed row: 1–2 label calls and at most 1 comment edit. The limits on sub-issues: 100 per parent, 8 levels ([adding sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)); the sub-issue add and remove endpoints note they can trigger secondary rate limiting "if done too quickly" ([sub-issues REST](https://docs.github.com/en/rest/issues/sub-issues)).
- **UI:** the spec issue shows its sub-issues as a list with progress, each with assignee and labels; the row's comment is visible only on the ticket. So the at-a-glance board on GitHub's own UI is the sub-issue list (assignee, labels, open/closed), not the full row. Label changes post timeline events on the ticket; a heartbeat that flips labels fills the ticket's timeline.
- **Public repos:** labels and comments are public. Issue fields have their own visibility: **Restricted** (the default) is "visible to organization members and repository collaborators with at least read access", **Public** to anyone, and these settings "only apply to issues in public repositories" and are "enforced across the web UI, API, issue timeline events, and search suggestions" ([managing issue fields](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-fields-in-your-organization)). So a Restricted issue field is the one per-ticket place on a public repository that the public cannot read.

### D. A GitHub Projects (v2) board with custom fields

A project linked to the repository, holding the spec's tickets as items, with custom fields for the row: a single-select **Delegation state**, text fields for **Branch** and **Decision Requests**. Assignees, linked pull requests and the parent issue are built-in fields.

- **gh:** the `gh project` suite arrived in v2.31.0 ("New suite of `project` commands", [release](https://github.com/cli/cli/releases/tag/v2.31.0)). 2.102.0 has `create`, `link`, `field-create`, `field-list`, `item-add`, `item-list`, `item-edit` and more; `item-edit` sets **one field per invocation** for a non-draft issue (**gh help**). `gh issue edit --add-project` adds an issue to a project by title. Every `gh project` command needs the token scope `project` (`gh auth refresh -s project`), and `read:project` for reads ([API docs](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects); **gh help**). This is an extra scope every teammate must grant; the default `gh auth login` scopes do not include it (**UNCONFIRMED** which scopes are default).
- **Permissions:** project access is separate from repository access. Organization projects have a base role (No access, Read, Write, Admin) plus per-team or per-person roles; user-owned projects invite individuals only, as Read, Write or Admin ([access](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects)). Repository Write does not grant project Write: "This only affects collaborators for your project, not for repositories in your project" (same page). So each teammate is added to the project with Write, in addition to their repository role.
- **Concurrency:** the finest grain of all surfaces: `updateProjectV2ItemFieldValue` sets one field of one item; "You cannot add and update an item in the same call", and it cannot change Assignees, Labels, Milestone or Repository ([API docs](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects)). Two writers clobber only when they write the same cell, which the assignee partition already rules out. A row is several calls, so a reader can see a row half-updated.
- **Rate limits:** reading all items with their field values is one paginated GraphQL query (`gh project item-list --format json`), about 1 point per 100 items. Each changed cell is one mutation (5 secondary points). A beat that changes three cells of one row is 3 mutations. Limits: 50 fields per project, built-in included ([about Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)); 50,000 items including archived ([adding items](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-items-in-your-project/adding-items-to-your-project)).
- **UI:** the only surface built as a board: table, board and roadmap views, grouping and filtering, including by parent issue, so one view can show exactly one spec's tickets ([adding sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues): parent issues and sub-issue progress "also appear in Projects"). Each issue's sidebar shows its project field values. It is one click away from the spec issue, not on it.
- **Public repos:** a project's visibility is its own setting, changed by project admins and organization owners; a public project is viewable by "everyone on the internet", and items from a private repository are shown only to people with access to that repository ([visibility](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-visibility-of-your-projects)). So a **private project over a public repository** keeps the row's custom fields (branch, Decision Requests) off the public web while the tickets themselves stay public. The default visibility of a new project is not stated: **UNCONFIRMED**. Issue fields shown in a project follow their own visibility: only Public issue fields appear in public projects ([about issue fields](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields/about-issue-fields)).
- **Setup cost:** someone creates the project and its fields once, links it to the repository, and grants each teammate Write. A Chief of Staff joining the Team Run must find the project, which is a config or discovery question for the map.
