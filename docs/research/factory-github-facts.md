# GitHub facts the factory depends on

Research for [#483](https://github.com/mnaimfaizy/agent-kit/issues/483), a child of the map [#480](https://github.com/mnaimfaizy/agent-kit/issues/480) ("Wayfinder: Agentic Software Factory"). The factory moves issues through `factory:*` labels with a deterministic Dispatcher, records verdicts against a PR's head commit, and may auto-merge low-risk PRs. This note collects what GitHub does and does not do under that design. Facts only; the design decisions belong to the map.

- **Read on:** 2026-11-25. Docs pages carry no publish date, so a fact is dated by this read.
- **Sources:** primary only. docs.github.com pages, the Liquid source of those pages in the [`github/docs`](https://github.com/github/docs) repository where a rendered page hides an availability note (the `data/reusables/gated-features/*.md` and `data/features/*.yml` files decide what shows on github.com: a feature file that lists `fpt` applies to github.com Free/Pro/Team), the [GitHub Changelog](https://github.blog/changelog/), and the [claude-code-action docs](https://github.com/anthropics/claude-code-action/tree/main/docs).
- **This repository:** `mnaimfaizy/agent-kit` is **public and owned by a user account** (`gh api repos/mnaimfaizy/agent-kit`: `owner.type: "User"`, `visibility: "public"`, `allow_auto_merge: false`). Several answers below turn on that.
- **SILENT** marks a point the docs do not state. **AMBIGUOUS** marks wording that admits two readings. Both are listed again at the end.

## 1. Events from automation

| Writer                                          | Does a label, push or PR it makes start other workflows?                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GITHUB_TOKEN`                                  | **No**, except `workflow_dispatch` and `repository_dispatch`, which "always create workflow runs". A PR opened or updated by it (`pull_request` `opened`/`synchronize`/`reopened`) creates runs in an **approval-required** state that a user with write access must approve. Every other event it causes (`issues: labeled`, `push`, `pull_request: labeled`, comments) creates no run at all. |
| GitHub App installation token                   | **Yes.** The docs name it as the way "to trigger a workflow from within a workflow run". PR runs start without approval.                                                                                                                                                                                                                                                                        |
| Personal access token (classic or fine-grained) | **Yes**, same sentence. The docs say "personal access token" without splitting classic and fine-grained.                                                                                                                                                                                                                                                                                        |

- Rule and exceptions: [GITHUB_TOKEN concept page](https://docs.github.com/en/actions/concepts/security/github_token), [Triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) ("you can use a GitHub App installation access token or a personal access token instead of `GITHUB_TOKEN`").
- The approval-required state for bot-made PRs is new: [Changelog 2026-06-11, "Bot-created pull requests can run workflows if approved"](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/). The [`pull_request` event notes](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) say: "With the exception of `workflow_dispatch` and `repository_dispatch`, other `GITHUB_TOKEN`-triggered events do not create workflow runs at all." The feature flag (`data/features/actions-github-token-pull-request-approval.yml`) covers github.com (`fpt`, `ghec`), not GHES yet. Before this change, such PRs ran no workflows at all.
- A run waiting for approval has conclusion `action_required`: "neither passed nor failed" ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)). A required check from it stays unreported until approved.
- `claude-code-action`: by default it uses the Claude GitHub App's token (comments as `claude[bot]`); passing `github_token` makes it act as that token instead ([faq.md](https://github.com/anthropics/claude-code-action/blob/main/docs/faq.md)). The FAQ repeats the rule: "The `github-actions` user cannot trigger subsequent GitHub Actions workflows… use a Personal Access Token (PAT) instead… or use a separate app token of your own." Whether pushes made with the **Claude app's** token start workflows is **SILENT** in the action docs; by the GitHub rule above an App installation token does.
- Plan or ownership: none of this varies by plan or by user- vs organization-owned repository; the pages give no such condition.

**Consequence for the design:** a Dispatcher that writes `factory:*` labels with `GITHUB_TOKEN` cannot rely on an `issues: labeled` workflow to react. It needs either an App token / PAT for the write, a `workflow_dispatch`/`repository_dispatch` hand-off, or a scheduled sweep.

## 2. Merge queue and rulesets

### Availability

| Feature               | Public, user-owned         | Public, org-owned (Free) | Private, user Free | Private, Pro | Private, org Team | Private, org Enterprise Cloud |
| --------------------- | -------------------------- | ------------------------ | ------------------ | ------------ | ----------------- | ----------------------------- |
| Protected branches    | yes                        | yes                      | no                 | yes          | yes               | yes                           |
| Rulesets (branch/tag) | yes                        | yes                      | no                 | yes          | yes               | yes                           |
| Push rulesets         | no (private/internal only) | no                       | no                 | no           | yes               | yes                           |
| Auto-merge            | yes                        | yes                      | no                 | yes          | yes               | yes                           |
| **Merge queue**       | **no**                     | yes                      | no                 | no           | no                | yes                           |

- Merge queue: "Pull request merge queues are available in any public repository owned by an organization, or in private repositories owned by organizations using GitHub Enterprise Cloud" ([`gated-features/merge-queue.md`](https://github.com/github/docs/blob/main/data/reusables/gated-features/merge-queue.md); rendered on [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). **A user-owned repository has no merge queue on any plan**, so this repository cannot use one unless it moves to an organization.
- Rulesets: "available in public repositories with GitHub Free and GitHub Free for organizations, and in public and private repositories with GitHub Pro, GitHub Team, and GitHub Enterprise Cloud"; push rulesets "for the Team plan in internal and private repositories" ([`gated-features/repo-rules.md`](https://github.com/github/docs/blob/main/data/reusables/gated-features/repo-rules.md); [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Organization-wide rulesets are Enterprise only (same page).
- Protected branches and auto-merge: same split, Free public only, paid public and private ([`gated-features/protected-branches.md`](https://github.com/github/docs/blob/main/data/reusables/gated-features/protected-branches.md), [`gated-features/auto-merge.md`](https://github.com/github/docs/blob/main/data/reusables/gated-features/auto-merge.md)).
- The ruleset rule **"Require merge queue"** is documented only for GHEC and GHES (`data/features/repo-rules-merge-queue.yml` lists `ghec` and `ghes`, no `fpt`), so on the github.com Free/Pro/Team docs the queue is configured through a branch protection rule ([About protected branches, "Require merge queue"](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-merge-queue)). Whether the ruleset rule works for a Free public org repository regardless of the docs is **AMBIGUOUS**.
- Rule gated by ownership: "Required reviewers" (team reviewers) "is not available on user-owned repositories as they do not contain teams" ([Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).

### Requiring a check from a given App

- Yes, for both rulesets and branch protection. "When you add a required status check rule, you can select an app as the expected source of status updates. The app must be installed in the repository with the `statuses:write` permission, must have recently submitted a check run, and must be associated with a pre-existing required status check in the ruleset. If the status is set by any other person or integration, merging won't be allowed." ([Available rules, "Require status checks to pass before merging"](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging); same for [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging)).
- Without a source pin, "Any person or integration with write permissions to a repository can set the state of any status check in the repository" (same pages).
- Checks from Actions workflows all come from the one "GitHub Actions" App, so pinning the source to GitHub Actions does not tell one workflow from another. The docs advise that "job names are unique across all workflows" because duplicates give ambiguous results ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Separating verdicts by writer therefore needs a distinct App per verdict source.

### Can a token hold no bypass?

- Rulesets have no default bypass: bypass is granted by adding an actor to the ruleset's bypass list. Eligible: "Repository admins, organization owners, and enterprise owners", "The maintain or write role, or custom repository roles based on the write role", "Teams, excluding secret teams", "GitHub Apps", "Dependabot" ([`rulesets-bypass-step.md`](https://github.com/github/docs/blob/main/data/reusables/repositories/rulesets-bypass-step.md), [Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)). Bypass mode can be "Always allow" or "For pull requests only". So a GitHub App, `GITHUB_TOKEN` or PAT that is not on the list (and whose user is not in a listed role) holds no bypass.
- Whether a repository admin who is not on the bypass list is bound by a ruleset is **SILENT** on the ruleset pages; the example "blocks force pushes for all users except repository administrators" implies admins are bound unless listed.
- Branch protection, by contrast, exempts admins by default: "the restrictions of a branch protection rule do not apply to people with admin permissions to the repository" unless "Do not allow bypassing the above settings" is on ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).
- **User-owned repositories:** "Actors may only be added to bypass lists when the repository belongs to an organization" (same page, in the branch-protection section). Whether that also limits ruleset bypass lists on a user-owned repository is **AMBIGUOUS**. In a user-owned repository a PAT acts as its user: the owner is the admin, and collaborators have one fixed level ([Permission levels for a personal account repository](https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository)).

### Merge queue mechanics (for an org repository)

- Workflows must listen to `merge_group` (`checks_requested`); without it the required check is never reported and the merge fails ([Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks), [Events, `merge_group`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group)).
- "A user with write access to the repository can add the pull request to the queue" ([Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). `gh pr merge` queues or enables auto-merge; the GraphQL `enqueuePullRequest` mutation queues only if it can join now. On a queue-required branch, auto-merge works "even if Allow auto-merge is disabled for the repository" ([Merging with a merge queue](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue)).
- Whether a `merge_group` event caused by a `GITHUB_TOKEN`-driven enqueue starts workflows is **SILENT**.

### Auto-merge without a queue (what this repository can use)

- "People with write permissions to a repository can enable auto-merge"; it "merges a pull request automatically after all required reviews and status checks pass"; it "is disabled if someone without write permissions pushes new changes to the head branch" ([Automatically merging a pull request](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request)). The repository setting "Allow auto-merge" is currently off here.

## 3. Verdicts: check runs versus commit statuses

|                                                | Check run                                                                                                               | Commit status                                           |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| GitHub App (installation or user token)        | yes, "Checks" write                                                                                                     | yes, "Commit statuses" write                            |
| `GITHUB_TOKEN`                                 | yes, `checks: write` ("permits an action to create a check run")                                                        | yes, `statuses: write`                                  |
| Fine-grained PAT                               | **no**: no "Checks" permission exists for fine-grained PATs                                                             | yes, "Commit statuses" write                            |
| Classic PAT / OAuth app                        | **no**: "OAuth apps and authenticated users can view check runs and check suites, but they are not able to create them" | yes, `repo:status` (or `repo`)                          |
| Can a ruleset or branch protection require it? | yes                                                                                                                     | yes: "Required status checks can be checks or statuses" |

- Check runs: "Write permission for the REST API to interact with checks is only available to GitHub Apps" ([REST check runs](https://docs.github.com/en/rest/checks/runs)); App permission table lists `POST /repos/{owner}/{repo}/check-runs` under "Checks" write ([Permissions for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)); the fine-grained PAT table has no Checks section ([Permissions for fine-grained PATs](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)). `GITHUB_TOKEN` scopes: [Workflow syntax, `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions). "GitHub Actions generates checks, not commit statuses" ([About status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks)).
- Commit statuses: "Users with push access in a repository can create commit statuses for a given SHA"; limit "1000 statuses per sha and context"; the combined state uses the latest status per context ([REST commit statuses](https://docs.github.com/en/rest/commits/statuses)).
- Pinning the source App requires the App to hold `statuses:write` and to have "recently submitted a check run" (see section 2).
- **Which SHA counts:** "Required checks must pass on the latest commit SHA. Checks from earlier commits don't satisfy the requirement." If a test merge commit has its own status, that merge commit must pass; otherwise the head commit ([Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)). A new push resets every verdict.
- **A check from another workflow run counts.** Matching is by check name (or status context) on the commit, not by the run that produced it; nothing ties a required check to the PR's own `pull_request` run. A workflow started by `workflow_run`, `workflow_dispatch` or a schedule that creates a check run (or status) with the required name on the head SHA satisfies it, subject only to the source pin. Docs say this by construction (checks are per commit, any writer with write access may set them), not in a single sentence: **AMBIGUOUS** only in that no page states "any run" outright.
- Same name, both kinds: "If a check and a commit status have the same name, both must pass when that name is required" (troubleshooting page).
- Skips: a workflow skipped by path or branch filters leaves its check **Pending** and blocks merge; a job skipped by `if:` reports **Success** and does not block, "even if it is a required check" (troubleshooting page; [About status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks)).
- Plan or ownership: required checks need protected branches or rulesets, so they follow the availability table in section 2.

## 4. Scheduled workflows

- **Shortest interval:** "The shortest interval you can run scheduled workflows is once every 5 minutes." Cron is POSIX; UTC by default, with an optional IANA `timezone` key ([`actions-scheduled-workflow-example.md`](https://github.com/github/docs/blob/main/data/reusables/repositories/actions-scheduled-workflow-example.md), rendered on [Events, `schedule`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)).
- **Delays and drops:** "The `schedule` event can be delayed during periods of high loads… High load times include the start of every hour. If the load is sufficiently high enough, some queued jobs may be dropped." Advice: schedule off the top of the hour (same page). No bound on the delay is given: **SILENT**.
- **Default branch only:** "Scheduled workflows will only run on the default branch", on its latest commit (`GITHUB_SHA` = last commit on the default branch); the workflow file must exist there (same page).
- **60-day disable:** "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." Also disabled by default in forks of public repositories ([`scheduled-workflows-disabled.md`](https://github.com/github/docs/blob/main/data/reusables/actions/scheduled-workflows-disabled.md)). It applies to **public** repositories; this one is public. What counts as "repository activity" (does a bot's label or comment count?) is **SILENT**. A commit by a write user that changes the `cron` line reactivates the workflow and makes that user the run's `actor`.
- **Concurrency groups as a lock** ([`actions-group-concurrency.md`](https://github.com/github/docs/blob/main/data/reusables/actions/actions-group-concurrency.md), [Workflow syntax, `concurrency`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)):
  - "There can be at most one running job or workflow in a concurrency group at any time", per repository; group names are case-insensitive and shared across all workflows of the repository.
  - Default `queue: single`: at most one pending; a newer queued run **cancels** the pending one. With `cancel-in-progress: true` the running one is cancelled too.
  - New `queue: max`: up to 100 pending runs, extra ones cancelled; cannot be combined with `cancel-in-progress: true`. Feature flag `actions-nga` covers github.com (`fpt`, `ghec`).
  - Order is FIFO by the time each started waiting on the group, but "ordering is not guaranteed".
  - So a group serializes Dispatcher runs within one repository (a mutual-exclusion lock), but with the default queue it drops intermediate triggers, and it does nothing about writers outside Actions (a human, or another repository).
- Plan or ownership: none of these vary by plan in the docs; only the 60-day rule depends on visibility.

## 5. Locking on an issue

- **No compare-and-swap on writes.** "Conditional requests for unsafe methods, such as `POST`, `PUT`, `PATCH`, and `DELETE` are not supported" unless an endpoint says otherwise ([REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). The labels and assignees endpoints say nothing about conditions or atomicity ([REST labels](https://docs.github.com/en/rest/issues/labels), [REST assignees](https://docs.github.com/en/rest/issues/assignees)).
- **Labels:** "Add labels" adds to "the issue's existing labels" (idempotent, no error if already present: the docs list no such error); "Set labels" "Removes any previous labels and sets the new labels" (last writer wins, and can silently drop a label another writer just added); "Remove a label" "returns a 404 Not Found status if the label does not exist" (**AMBIGUOUS**: not on the issue, or not in the repository).
- **Assignees:** "Users already assigned to an issue are not replaced", up to 10; assignees without permission are dropped silently ([REST assignees](https://docs.github.com/en/rest/issues/assignees)).
- **Comments:** each create is a new comment; nothing orders two comments beyond their ids and timestamps. **SILENT** on ordering guarantees.
- **What a race looks like:** two Dispatchers that both read `factory:ready-for-agent`, then both add `factory:locked` (or both add themselves as assignee) **both succeed**. Neither call reports that the other won. Add-label and add-assignee are commutative, so the result looks like one claim (one label) or shows two assignees; a "Set labels" write can erase the other's change. No GitHub primitive tells the loser it lost.
- What does serialize: a concurrency group (section 4), if every writer is an Actions run in the same repository using the same group. Outside that, a claim must be checked after the write (re-read, and use a tiebreak such as the earliest `labeled` event in the issue's event history). The docs give no guarantee about webhook delivery order: **SILENT**.
- Plan or ownership: no difference stated.

## 6. Labels: who may add or remove, and the actor in the event

- **No per-label restriction exists in the docs.** Permission is per role, for all labels at once: "Apply/dismiss labels" is held by Triage, Moderate, Write, Maintain and Admin, not Read; creating/editing labels needs Moderate or higher; deleting needs Write or higher ([Repository roles for an organization](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)). Nothing lets a repository reserve `factory:*` labels for one actor: **SILENT** (no such feature is documented; rulesets govern refs and pushes, not labels).
- **User-owned repositories** have only owner and collaborators; collaborators can "Manage labels for issues and pull requests" and "Create, merge, and close pull requests"; "Collaborators can't have read-only access" ([Permission levels for a personal account repository](https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository)). So in this repository every collaborator can set any `factory:*` label; outsiders (no write) cannot label at all.
- **Tokens:** labels need "Issues" (or "Pull requests") write for fine-grained PATs and Apps ([fine-grained PAT permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)); `GITHUB_TOKEN` needs `issues: write` or `pull-requests: write` ([Workflow syntax, `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)).
- **Actor in the payload:** the `issues` event with `labeled`/`unlabeled` carries `issue` and `label`; `assigned` carries `assignee`; "Most webhook payloads include a `sender` property identifying the user who triggered the event", described as "A GitHub user"; when GitHub can't resolve a user, `sender` is the `ghost` account, so do not assume `sender` always identifies the person who caused the event ([Webhook events and payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads#issues)). How an App or `GITHUB_TOKEN` appears in `sender` (a `[bot]` login, `type: "Bot"`) is not spelled out on that page: **SILENT** there.
- In a workflow, `github.actor` is "The username of the user that triggered the initial workflow run", `github.actor_id` "The account ID of the person or app", `github.triggering_actor` the one who started a re-run; "Any workflow re-runs will use the privileges of `github.actor`" ([Contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)). The Dispatcher must check the actor's permission itself (for example `GET /repos/{owner}/{repo}/collaborators/{username}/permission`) if a label's author matters.
- `claude-code-action` checks write access for issue, PR, comment and review events, and by default ignores bots unless `allowed_bots` lists them; "Allowed bots are not checked for repository permissions" ([security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)).
