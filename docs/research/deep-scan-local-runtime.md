# Which local runtime gives a deep scan a VM boundary on macOS, Windows and Linux

Research for [#341](https://github.com/mnaimfaizy/agent-kit/issues/341), child of map [#332](https://github.com/mnaimfaizy/agent-kit/issues/332) (Deep scan: sandboxed dynamic security audit). It follows decision 3 of [#337](https://github.com/mnaimfaizy/agent-kit/issues/337): a local deep scan runs Claude Code and the target together inside one disposable sandbox, which must have a VM boundary from the host OS, or the scan refuses to run.

- **Read on:** 2026-11-19. Docs pages carry no publish date, so each fact is dated by the read.
- **Builds on:** `docs/research/deep-scan-sandbox-environments.md` (branch `research/deep-scan-sandbox-environments`, ticket #333) and `docs/research/deep-scan-claude-code-sandbox.md` (branch `research/deep-scan-claude-code-sandbox`, ticket #334). Settled there and not repeated: plain Docker shares the host kernel; gVisor, Kata, Firecracker and Docker Sandboxes add a second kernel or a hypervisor; Docker Sandboxes' deny-by-default proxy; the credential exposure table for whole-process boundaries. This note closes #333's gap on Docker Sandboxes' host OSes and hardware.
- **Sources:** vendor docs and source repositories only. Nothing was installed or run.
- **INFERENCE** marks a conclusion drawn from stated facts that no source states outright. **UNCONFIRMED** marks a point no source settles.
- This note states facts and trade-offs. It picks no runtime: that is for [#338](https://github.com/mnaimfaizy/agent-kit/issues/338) (network and secrets) and the spec.

## Per runtime

### Docker Desktop

- **Boundary from the host:** "Docker Desktop runs all containers inside a customized Linux virtual machine (except for native Windows containers)", which "adds strong isolation between containers and the host machine, even when containers run as root" [DD1]. On Linux too, "Docker Desktop on Linux runs a Virtual Machine (VM)" that "requires KVM support" [DD2]. Plain Docker Engine on Linux has no VM (settled in #333).
- **Not a boundary between sandboxes.** Every container runs in the same VM [DD1]. Without ECI, a privileged container gets "access to VM internals and Docker Engine" [DD1]. INFERENCE: two deep scans on one Docker Desktop share a kernel, so the per-sandbox boundary is namespaces, not a VM.
- **Windows WSL 2 backend:** the engine lives in a `docker-desktop` WSL distribution [DD5]. Microsoft: WSL 2 distributions "run as isolated containers inside of the WSL 2 managed VM" and "share the same network namespace, device tree ... CPU/Kernel/Memory/Swap" [W1]. INFERENCE: on WSL 2 the VM boundary is between Windows and all WSL distros together, so an escape into the VM reaches the user's other distros' kernel and network. Docker itself suggests Hyper-V or Docker VMM plus ECI "for stricter isolation" [DD5].
- **Files:** containers reach only folders configured for file sharing [DD1], but the macOS/Linux defaults include `/Users`, `/Volumes`, `/private`, `/tmp` and `/var/folders` [DD6]. INFERENCE: on macOS a sandbox that bind-mounts any path under the user's home works without extra config, so the image definition, not Docker Desktop, has to keep host mounts narrow.
- **Network:** `host.docker.internal` "Resolves to the internal IP address of your host" [DD7]. "All outbound container network traffic originates from the `com.docker.backend` process" on the host [DD8]. Docker Desktop has no per-container hostname allowlist by default; air-gapped container enforcement is a Hardened Docker Desktop feature [DD8][DD6].
- **ECI** (Sysbox instead of runc, user namespaces) prevents containers from "breaching the Docker Desktop virtual machine or other containers" [DD9] and needs sign-in plus Docker Business [DD6].
- **Cost:** free for "small businesses (fewer than 250 employees AND less than $10 million in annual revenue)", personal use, education and non-commercial open source; "Paid subscriptions are also required for government entities" [DD3][DD4].

### Docker Sandboxes (`sbx`)

- **Hosts and hardware** [S4], the gap left by #333:
  - macOS: "macOS Sonoma version 14 or later", "Apple silicon". No Intel Macs.
  - Windows: "Windows 11", "A 64-bit Intel or AMD processor", "Windows Hypervisor Platform for local sandboxes", turned on with `Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -All` (elevated). No Windows 10, no Windows on Arm.
  - Linux: "Ubuntu 24.04 or later", x86-64 or Arm64, KVM on and the user in the `kvm` group. "Docker does not test or support Docker Sandboxes on Ubuntu derivatives". Inside a VM or VDI, nested virtualization is required.
  - "You don't need Docker Desktop or Docker Engine to use `sbx`."
- **Boundary:** each sandbox is "a lightweight microVM with its own Linux kernel"; "processes inside the VM are invisible to your host and to other sandboxes"; "The agent has no path to your host Docker daemon" (each sandbox has its own Engine) [S5]. The docs name no hypervisor per OS beyond WHP and KVM on the install page [S4][S5].
- **Files:** `sbx run` mounts the current directory; "The agent can read, write, and delete any file within that directory" [S10]. Direct mounts use "a filesystem passthrough", changes "instant" both ways [S1]. Clone mode mounts the repo read-only at `/run/sandbox/source` and works in a private clone [S1]. Mountless (`sbx create` with no path) keeps files in the VM [S7][S10]. A local sandbox "can write text to your host clipboard, but can't read" it [S5].
- **Network:** "All outbound TCP traffic from the sandbox routes through a proxy on your host"; HTTP(S) via a forward proxy, other TCP forwarded transparently [S1]. Deny-by-default; UDP off unless the experimental UDP feature is on; ICMP blocked [S6][S10]. Host services: `host.docker.internal` plus `sbx policy allow network localhost:<port>`; `127.0.0.1` does not reach the host [S8]. Inbound: `sbx port publish` [S7]. Credentials: the host proxy injects auth headers and "The raw credential values never enter the VM" [S6] (relevant to #338).
- **Destruction:** `sbx rm` deletes "the sandbox, its VM, and all of its contents" and, for clone mode, removes the `sandbox-<name>` remote from the host repo [S1]. It asks for confirmation; `--force` skips it and works with an active session; `sbx run --rm` removes on agent exit; `sbx prune` removes only stopped sandboxes [S7]. A directly mounted workspace stays on the host [S7].
- **Sign-in and cost:** `sbx login` "opens a browser for Docker OAuth" and is required [S4]. Sign-in gives each sandbox "a verified identity" for governance and Docker infrastructure [S9]. "The `sbx` CLI and local sandbox compute are free to use, including for commercial and professional work"; cloud sandboxes are pay-as-you-go; org governance is a separate paid subscription [S9]. Usage telemetry (command, success, duration, Docker username) is on by default, excludes prompts and code, and can be turned off with `sbx settings set telemetry.disabled true` or `SBX_NO_TELEMETRY=1` [S9].
- Claude Code's docs name it as a VM option: "a free, standalone product from Docker that does not require Docker Desktop" [CC1].

### gVisor on a Linux host

- Linux only: "gVisor supports x86_64 and ARM64, and requires Linux 5.6+" [G3]; "Today, gVisor requires Linux" [G6].
- **Is it a VM boundary?** Not in the hardware sense. The default platform is `systrap`; the KVM platform "uses the kernel's KVM functionality to allow the Sentry to act as both guest OS and VMM", yet "there is no virtualized hardware layer" and "the sandbox retains a process model" [G4]. gVisor describes its first principle as "similar to the security basis for a Virtual Machine" and warns "one should not assume that the mere use of virtualization hardware makes a system more or less secure" [G5]. Whether gVisor counts as "a VM boundary" for #337 decision 3 (which lists it alongside microVMs) is a spec wording call, not a fact the docs settle.
- **Host access:** the Sentry makes "a minimal set of host system calls"; file access goes through a Gofer and can be denied entirely; host networking, if enabled, lets it create host sockets [G5].
- **Install:** `sudo apt-get install -y runsc` auto-configures Docker; manual install is `sudo runsc install` then reload Docker; run with `--runtime=runsc` [G3][G2]. Root is needed to install. Auto-download in `runsc install` "will be dropped at the end of September 2026" [G3].
- macOS and Windows users could only run it inside a Linux VM they already have (for example Docker Desktop's VM). No gVisor or Docker page read documents that combination (UNCONFIRMED).

### Kata Containers and Firecracker on a Linux host

- **Kata:** lightweight VM per pod with its own kernel [K1]; runs on x86_64 (VT-x/SVM), aarch64, ppc64le, s390x [K3]; "requires nested virtualization or bare metal" [K4]. `kata-runtime check` reports whether the host can run Kata [K3]. It is "a containerd shimv2 runtime" [K3]; the preferred install is a Kubernetes Helm chart [K4]. `--net=host` is not supported [K5]. Inside the guest, `mount` shows the root as `kataShared on / type virtiofs` [K6].
- **Firecracker direct:** "x86_64 and aarch64 Linux", read/write `/dev/kvm`, an uncompressed guest kernel and an ext4 rootfs, a TAP device and an iptables MASQUERADE rule set up by hand [F2]. Devices are virtio net, block and vsock plus a serial console; block devices "are backed by files on the host"; there is no directory sharing; "Firecracker does not perform any network traffic filtering"; production should start it through the jailer [F3]. A guest `reboot` shuts it down, since it has no guest power management [F2].
- Neither runs on macOS or Windows hosts [K3][F2].

### Dev containers on top of any of these

- The spec defines no isolation boundary; it assumes Docker-style tooling [DC1]. `runArgs` is "An array of Docker CLI arguments" [DC2]. INFERENCE: a devcontainer can select gVisor with `"runArgs": ["--runtime=runsc"]` on a host where `runsc` is registered, but the boundary is still the runtime's.
- `shutdownAction` values are `none`, `stopContainer` (default for an image or Dockerfile) and `stopCompose` [DC2]: stop, not remove. "It is not a strict requirement to keep a development container after it has been stopped" [DC1]. Destruction is the tool's or the maintainer's job.
- Claude Code's dev container guide: the host repository is bind-mounted, edits "appear in your local repository", and with `--dangerously-skip-permissions` a dev container does not stop a malicious project "exfiltrating anything accessible inside the container, including the Claude Code credentials" [CC2]. Claude Code's sandbox page classes a dev container as a container, and a dedicated VM or microVM as "the strongest separation" [CC1].

## Detecting that the boundary is present

No source documents a check a process **inside** the sandbox can trust:

- gVisor's own verification, `docker run --runtime=runsc -it ubuntu dmesg`, comes with the warning that "this is easily replicated by an attacker", so it should not be used in security-sensitive contexts [G2].
- Kata's guest shows a `virtiofs` root mount [K6]; ECI shows a non-root `uid_map` such as `0 100000 65536` [DD9]. Neither page offers these as security checks.
- Docker Sandboxes' docs have no step to verify the agent runs in a VM [S5].

Checks that run on the **host**, before anything from the target runs, are documented:

- `kata-runtime check` (host can run Kata) [K3]; `lsmod | grep kvm` for KVM on Ubuntu [S4]; `docker run --runtime=runsc` fails if `runsc` is not registered (INFERENCE from [G3]).
- Docker Desktop on Linux "creates and uses a custom docker context" [DD2], so the active context distinguishes it from plain Engine (INFERENCE; the context name is not quoted here).

INFERENCE: since the target and Claude Code share the sandbox, a check run by Claude Code inside it is only as good as the moment it runs (before the target is built). The more robust shape is a host-side launcher that starts the runtime itself (for example `sbx run`, or `docker run --runtime=runsc`) and refuses when that runtime is missing, so the boundary is a property of how the scan was started rather than something the guest reports.

## Key trade-offs

- **Coverage vs. strength.** Docker Desktop runs on all three OSes and the widest range of hardware (Intel Macs, Windows 10) [DD3][DD4], but gives one VM for all containers and, on WSL 2, a VM shared with the user's other distros [DD1][W1]. Docker Sandboxes gives a VM per sandbox with its own Engine and a deny-by-default proxy [S5][S6], but only on Apple silicon macOS 14+, x86-64 Windows 11 and Ubuntu 24.04+ [S4].
- **Linux options are free but Linux-only and hands-on.** gVisor is the lightest install [G3] but is not hardware virtualization by default [G4]; Kata and Firecracker are real microVMs [K1][F3] with the most setup, and Firecracker leaves file sharing and egress filtering entirely to the maintainer [F3].
- **Sign-in and licensing.** `sbx` requires a Docker OAuth sign-in even for free local use [S4][S9]. Docker Desktop requires a paid subscription for larger companies and governments [DD3], and ECI requires Business [DD6]. gVisor, Kata and Firecracker need neither.
- **Destruction.** `sbx rm` removes the VM and everything in it [S1]; on Docker Desktop removing the container leaves the shared VM; a dev container is stopped by default, not removed [DC2]. In every runtime a directly mounted workspace is the host's own files and survives [S7][CC2]; only clone or mountless modes keep target writes off the host [S1].
- **Host reachability.** Docker Desktop containers reach host services at `host.docker.internal` with no policy [DD7]; Docker Sandboxes requires an explicit allow rule for the same name [S8]. This bears on #338.

## Gaps

- **Kata with Docker:** the how-to says that with Kata 2.x "Docker can no longer be used to create containers using a Kata Containers runtime" [K6], while the limitations page says Kata has supported Docker since 22.06 [K5]. Not reconciled here.
- **Docker Sandboxes on macOS:** the docs name WHP (Windows) and KVM (Linux) but no hypervisor for macOS [S4][S5]. The `sbx rm` CLI reference page rendered empty; behaviour above comes from the architecture and usage pages [S1][S7].
- **Docker Sandboxes offline / sign-in lapse:** no page read says whether local sandboxes run without network access to Docker's sign-in service.
- **Docker Desktop VM kernel sharing** between containers is implied by "all containers inside a customized Linux virtual machine" [DD1] but not stated; the Docker security FAQ does not call the VM a security boundary in so many words.
- **gVisor inside Docker Desktop's VM** (the only way to get gVisor on macOS/Windows) is not documented by either project.
- **Windows Home:** Docker Desktop's install page lists Enterprise, Pro and Education editions [DD4]; whether Home is supported was not settled from the text read.
- **No vendor documents a tamper-proof in-guest check** that a VM boundary is present.
