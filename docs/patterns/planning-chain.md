# Pattern guide: the planning chain

A way to turn a feature idea into work that builders can run unattended without stacking new work on broken or unfinished work: grill the plan against the glossary and the decision records, publish it as one PRD issue, and slice it into vertical issues that each say how much checking they need, whether a person must decide first, and what they wait for. A slice closes only when its run ended clean, and the PRD is gated once, on the branch that assembles all of its slices. This is a **Pattern guide** ([ADR 0012](../adr/0012-pattern-guides-are-docs-a-consumer-adapts.md)): you read it, copy the skeleton, and adapt it. Agent-kit does not install or upgrade it.

Skeleton to copy: [`examples/patterns/planning-chain/`](../../examples/patterns/planning-chain/)

- [`prd-issue.md`](../../examples/patterns/planning-chain/prd-issue.md): the PRD issue template, with the assembled-branch gate section the chain adds.
- [`slice-issue.md`](../../examples/patterns/planning-chain/slice-issue.md): the slice issue template, with its acceptance criteria, its decision for a person and its blocking edges. Its parent is the sub-issue link, not a line in its body.
- [`labels.json`](../../examples/patterns/planning-chain/labels.json): the label set, each label with its rule.

This skeleton is templates only. It has no agent body, no `SKILL.md` and no runner: the steps of each link in the chain are skills from the [Companion library](../../README.md#companion-library), and this page does not restate them. What it describes is the contract between those steps: what each one hands the next, and what a dispatcher reads.

## The problem

A plan that goes straight from a conversation to a list of issues, and from there to builders running overnight, goes wrong in predictable places:

- **The plan uses words the code does not.** A plan says "account" where the glossary has two terms for two things, or contradicts a decision the repository already recorded. Nobody notices until a builder implements the wrong one.
- **The issues are layers.** "Add the schema", "add the endpoint", "add the screen". None of them can be checked on its own, so the first one that can be tested is the last one, and every earlier mistake surfaces there.
- **Dependencies live in prose.** "Do this after the settings work" is in a sentence that a dispatcher cannot read, so it starts a slice before its blocker. Kept in two places, as a "blocks" list on one issue and a "blocked by" list on the other, the two disagree after the first edit.
- **A slice closes on any commit.** A builder says in its last message that it did not deliver part of the slice, commits what it has, and the slice is closed as done. The slice behind it is released and builds on the missing part (the worked example below).
- **A per-slice gate stops the night.** Each slice is checked against the head it was cut from, and a failed check aborts the run. In one repository the first two slices of a six-slice plan both failed the check overnight, because of a fault in the check's own environment, not the work. Run three times, it stopped there each time: about forty agent invocations, and nothing integrated. Two slices that each passed alone could also break each other, and no per-slice check could see it.

## The moving parts

```text
  grill               PRD issue                slices (sub-issues)            dispatcher
┌──────────────┐  ┌──────────────────┐     ┌──────────────────────────┐   ┌───────────────────┐
│ one question │  │ label: prd       │     │ one tier label           │   │ starts an open    │
│ at a time;   │─▶│ glossary terms,  │────▶│ afk or hitl              │──▶│ afk slice with the│
│ glossary and │  │ decisions linked;│ cut │ Blocked by: one record   │   │ dispatch label,   │
│ records      │  │ assembled-branch │     │ dispatch label on afk    │   │ not integrated,   │
│ updated      │  │ gate             │     └──────────────────────────┘   │ blockers closed   │
└──────────────┘  └────────┬─────────┘                                    └─────────┬─────────┘
                           │ verdict comment     ┌──────────────────────────────────┘
                           │                     ▼
                  ┌────────┴──────────────────────────────┐  clean: close, release dependents
                  │ assembled branch: every slice's       │  not clean: integrated, open,
                  │ commits; gated once, against default  │  ready-for-human, items listed
                  └───────────────────────────────────────┘
```

1. **Grilling** stress-tests the plan, one question at a time, against the glossary and the decision records, and updates the glossary as each term is settled. In the Companion library this is `grill-with-docs`, which loads its `grilling` and `domain-modeling` skills.
2. **The PRD issue** is the agreed plan, published once, in the glossary's terms. The library's `to-spec` writes it (the library calls it a spec). The chain adds the `prd` label and one section: the gate to run on the assembled branch.
3. **The slices** are vertical issues cut from the PRD, each a sub-issue of it. The library's `to-tickets` cuts them (it calls them tickets). The chain adds four things to each: a tier label, an `afk` or `hitl` marker, its blocking edges in one place, and the dispatch label when it may start.
4. **The dispatcher** reads the slices, starts each one that is ready, integrates its commits onto the assembled branch, and decides whether to close it. It is yours. Agent-kit's [`orchestrate`](../orchestrate.md#spec-mode) reads a spec's sub-issues, their "Blocked by" sections and native edges, and their triage labels, so it can be the dispatcher; the tier, the marker and the closing rules below are what you check it against, or add.
5. **The assembled-branch gate** runs once, when every slice is in, on the assembled branch against the default branch, and posts its verdict on the PRD.

The skill names above are the library's at the time of writing. It is not on Agent-kit's Release line and renames its skills, so check its current names.

## The rules, and why each one exists

| Rule                                                                                                                                                                                                                                                                           | Why                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A plan is grilled before it is published. Grilling ends with the glossary and any new decision records committed, so the PRD can use and link them.                                                                                                                            | A term settled in the conversation and not written down is settled for that conversation only. A builder working from the PRD reads the glossary, not the chat.                                                                                                              |
| One PRD issue per feature, labelled `prd`, in the glossary's terms and with no file paths. Each decision it rests on links its record.                                                                                                                                         | The slices, the builders and the gate all point back to one issue. File paths in a plan go stale before the slices are built; a decision record does not.                                                                                                                    |
| Slices are vertical: each makes one behaviour work end to end, through every layer, and can be verified on its own. Each is a sub-issue of its PRD.                                                                                                                            | A layer cannot be tested alone, so a horizontal slice hides its mistakes until the last layer lands. A sub-issue is a link a dispatcher reads, where a list in the PRD's body, or a parent line in the slice's, would be a copy of it that a re-parented slice leaves wrong. |
| Each slice carries exactly one gate tier label: `tier:mechanical`, `tier:standard` or `tier:full`. A slice with none is not ready.                                                                                                                                             | The tier is chosen once, when the work is split and the whole plan is in view, not by a builder that would rather do less ([tiered quality gates](tiered-quality-gates.md)). Treating a missing tier as a default would let a forgotten label pick the depth.                |
| Each slice is exactly one of `afk` or `hitl`. A `hitl` slice says, in its Decision needed section, what a person decides and who, and gets `ready-for-human`, never the dispatch label.                                                                                        | A builder that hits an open question in the night either stalls or guesses. Marking it at slicing time sends it to a person first, and the section says what they are being asked.                                                                                           |
| Each blocking edge is recorded once: under the slice's `Blocked by`, or as the tracker's native dependency link, never both. Only an issue that starts a list item is an edge.                                                                                                 | A dispatcher can read an edge; it cannot read "after the settings work". Two records of one edge disagree after the first edit, and a reverse list on the blocker is a second record. The list-item rule lets prose say "not blocked by #12" safely.                         |
| The dispatch label goes only on an `afk` slice. A dispatcher starts an open slice that has it, is not `integrated`, and whose blockers are all closed.                                                                                                                         | One label says "may start", and the edges say "not yet". Keeping readiness a fact the dispatcher computes, rather than a "blocked" label someone keeps in step, leaves nothing to forget.                                                                                    |
| The dispatcher puts the PRD's body in each slice's brief.                                                                                                                                                                                                                      | A builder in a sandbox may have no credentials for the tracker. A slice that leaned on its PRD for its copy, its colours or its offline rule then has none of them, and builds without them.                                                                                 |
| A builder ends its run with a list of what it did not do or could not verify: a blocking review finding it left, a criterion not delivered, a device-only check, a source it could not read, a disagreement between the slice and its PRD.                                     | An honest list is not a failure. A run's last message is where a builder says what it knows is missing, and without a list that something reads, that message reaches nobody.                                                                                                |
| A slice closes only on a clean outcome: the builder signalled completion and its list is empty. Otherwise it is integrated but stays open, swaps the dispatch label for `ready-for-human`, gets a comment listing each item, and its dependents wait until a person closes it. | Closing on any commit is how a slice that said "not delivered" released the slice that needed it. A review verdict is not the signal: the review runs before the builder's fixes, so it reads the same whether the fixes landed or not.                                      |
| A slice that produced commits is labelled `integrated` whether or not it closed, and is never dispatched again.                                                                                                                                                                | A re-run that keys on "closed" would build a held slice a second time on top of its own commits. "Integrated" and "finished" are two facts, so they are two labels.                                                                                                          |
| A PRD is gated once, on the assembled branch against the default branch, when every slice is in. The gate reports, as a comment on the PRD, and does not stop the run or undo a slice.                                                                                         | The assembled branch is what will be reviewed and merged, and the only scope where two slices that break each other show. One gate instead of one per slice is one install and one run. A gate that stops the run turns a fault in the gate into a lost night.               |
| A gate failure is not fed back to a builder automatically. A person reads it.                                                                                                                                                                                                  | Each builder run is a cold start at full price, and a failed gate is as often the gate's environment as the code. A builder told to fix code that was never broken spends a run on nothing.                                                                                  |
| An issue with no PRD keeps a gate of its own, on its own branch, and that gate blocks.                                                                                                                                                                                         | Its branch is the deliverable, so there is no later gate to defer to.                                                                                                                                                                                                        |
| The chain's own documents link to the Companion skills for each step's procedure and never restate it.                                                                                                                                                                         | The library changes its skills on its own schedule. A restated procedure is a fork of it that nothing updates ([instruction layout](instruction-layout.md)).                                                                                                                 |

### Worked example: the slice that said "not delivered"

One repository ran a plan of several slices unattended. Its dispatcher closed a slice as soon as the slice had commits, and closing a slice released every slice it blocked.

One slice could not deliver a setting it was asked for, and said so in its last message, under a heading that read "Not delivered". It had committed the rest, so it was closed. A later slice, blocked by it, was released and built a toggle for that setting. The toggle switched nothing. Three other slices finished with a blocking review finding still open, and were closed the same way.

Nothing was hidden: each builder had written down what it left. Nothing read it. The fix was the outcome rule above: the dispatcher reads the builder's list, closes a slice only when the list is empty, and otherwise holds it open for a person and keeps its dependents waiting.

## Failure modes

- **The list is only as honest as the builder.** A builder that leaves an item off its list closes clean. What the rule adds is that a builder's own caveats now hold the work, where before nobody read them. A run whose last message cannot be read counts as not clean.
- **A held slice stops its dependents.** A plan can end with slices waiting for a person and the slices behind them never started. That is the rule working. Have the dispatcher report every held slice at the end, and exit non-zero while any remain, so the morning starts there.
- **One gate loses which slice broke it.** A red gate says the assembled branch is broken, not which slice did it. Integrate each slice as its own ordered commits, keep each slice's branch, and bisect the assembled branch's commits from the default branch.
- **A broken slice spreads.** Without a per-slice gate, a broken slice is built on until the end. Nothing is pushed until a person has read the verdict, every slice's branch survives, and the assembled branch can be reset.
- **The Companion skills do not add the chain's labels.** The library's slicing skill applies its own triage label and blocking edges. It knows nothing of tiers or the `afk` and `hitl` marker. Add them when you approve the breakdown, or in the tracker document the library reads its label vocabulary from, and check them before dispatching.
- **An edge is recorded twice.** A slice whose `Blocked by` section and native link disagree is blocked by whichever one the dispatcher reads. Pick one record for the repository, and say which in your tracker document.
- **The library renames a step.** A skill that the chain names by its old name no longer loads. Name the steps in one place, your tracker document or your always-on file's choosers, and update that place when you update the library.

## Adopting it

1. **Adopt the Companion library.** Install it as the [Companion library](../../README.md#companion-library) section says, and set up its tracker and triage-label documents. Agent-kit's own [`docs/agents/triage-labels.md`](../agents/triage-labels.md) shows the shape.
2. **Create the labels.** Create each label in `labels.json`, renamed to your vocabulary if you like, keeping each label's rule. Map `ready-for-agent` and `ready-for-human` to your triage roles.
3. **Copy the templates.** Put `prd-issue.md` and `slice-issue.md` in your tracker's template folder, such as `.github/ISSUE_TEMPLATE/`.
4. **Fill in every placeholder.** Each is written `<like this>`. They cover the default branch, the assembled-branch gate's command, and the template folder.
5. **Choose the dispatcher.** Use `orchestrate`, or your own, and check it against the rules: it starts only ready `afk` slices, puts the PRD in each brief, reads each builder's list, closes only on a clean outcome, labels `integrated`, and posts the gate's verdict on the PRD. Write down whatever it does not do, and who does it instead.
6. **Try it on purpose.** Slice a small plan into two slices, one blocked by the other. Have the first one's builder list one item it did not do, and check that the first stays open as `ready-for-human` and the second is not started.
